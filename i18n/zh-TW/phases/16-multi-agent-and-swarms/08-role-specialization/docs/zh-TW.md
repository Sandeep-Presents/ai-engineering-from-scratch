# 角色專門化分工——規劃者、審查者、執行者與驗證者（Role Specialization — Planner, Critic, Executor, Verifier）

> 2026 年最為普及的多 Agent 任務拆解典範：一人專職規劃、一人專注執行、一人負責批判審查或客觀驗證。MetaGPT（arXiv:2308.00352）將此架構形式化為深植於角色 prompt 中的標準作業程式（SOP）——涵蓋產品經理、架構師、專案經理、工程師與 QA 測試工程師——恪守 `Code = SOP(Team)` 的核心公式。ChatDev（arXiv:2307.07924）則透過「對話鏈」將設計師、程式設計師、審查員與測試員串聯在一起，並引入了「溝通式去幻覺（communicative dehallucination）」機制（各 agent 在遭遇細節缺失時主動向上游索取而非盲目臆造）。其中，驗證者的存在至關重要：Cemri 等人（MAST 失效分類研究，arXiv:2503.13657）指出，多 agent 系統的每一個失敗都可追溯至驗證機制缺失或失效。PwC 的正式環境實測更指出，在 CrewAI 中僅僅引入結構化驗證迴圈，就讓系統任務準確率獲得了高達 7 倍的飛躍（從 10% 暴增至 70%）。

**Type:** Learn + Build
**Languages:** Python (stdlib)
**Prerequisites:** Phase 16 · 04 (Primitive Model), Phase 16 · 05 (Supervisor)
**Time:** ~60 minutes

## Problem｜問題

平庸泛化的多 Agent 系統只會產出平庸泛化的平庸結果。讓三位程式設計師在同一個群組對話中協同，產出的只不過是同一種平庸程式碼的三種微小變體。你可以繼續盲目追加更多 agent、拉長對話輪次，系統品質依然無法跨越及格門檻。

真正的解法絕非盲目堆砌更多 agent——而是引入具備**截然不同專業分工**的異質 Agent。賦予彼此截然不同的角色定義。給予審查者規劃者所不具備的專屬分析工具。為驗證者配備冷酷客觀的自動化測試套件。因此，系統內部會產生基於實證基礎的良性爭鳴與精準修正，而非停留於平行胡亂猜測。

## Concept｜核心概念

### 四大經典標準角色

**規劃者（Planner）。** 通讀全域目標，產出結構化的步驟清單或技術規格說明書。工具：知識檢索、文件查詢。產出結果：結構化執行規劃。

**執行者（Executor）。** 每次嚴格讀取單一步驟的規劃，產出工件。工具：實際作業工具（程式碼編譯器、終端機 shell、API 用戶端）。產出結果：工件。

**審查者（Critic）。** 對照規劃者的原始意圖，對執行者交付的產出進行品質審查。工具：唯讀檢視工件的權限、靜態程式碼分析器。產出結果：附帶具體反駁理由的接受或打回裁定。

**驗證者（Verifier）。** 讀取工件並執行確定性的客觀程式碼檢驗。工具：自動化測試執行器、型別檢查器、結構描述驗證器。產出結果：附帶確鑿實證的通過或失敗判定。

審查者是主觀的、帶有審美與架構偏好的，通常由進階 LLM 擔任。驗證者則是冷酷客觀的、具備確定性的，通常直接由底層程式碼或測試常式擔任。兩者絕非同一個角色。

### MetaGPT 的 SOP 模式

MetaGPT（arXiv:2308.00352）將軟體工程領域的標準作業程式（SOP）直接編碼進各角色的系統 prompt 中：

- **產品經理（Product Manager）** 負責撰寫產品需求文件（PRD）。
- **架構師（Architect）** 負責輸出系統架構設計。
- **專案經理（Project Manager）** 負責進行詳細的任務拆解與排程。
- **工程師（Engineer）** 專注於具體實作。
- **QA 工程師（QA Engineer）** 專門執行自動化測試。

每個角色都有嚴格的輸入／輸出結構描述。角色 prompt 清楚界定了該角色「是什麼」以及「必須產出什麼」。這正是 `Code = SOP(Team)` 的深層哲學——確定性的 SOP 能將一群容易發散的 LLM 馴服為高度可預測的高效生產管線。

### ChatDev 的溝通式去幻覺機制（Communicative Dehallucination）

ChatDev 引入了一項極具啟發性的關鍵架構：當執行者在實作中發現需要某些規劃中未曾提及的具體細節時，它會主動向上游的設計師發起明確詢問，確認細節後才繼續前進。這可避免 LLM 習慣性編造看似合理細節的典型失誤。

具體實作方式：在角色 prompt 中硬性規定「當你需要未被明確賦予的具體資訊時，在生成任何輸出前，必須指名道姓向相應的角色發起詢問確認」。

### 為什麼驗證者（Verifier）最重要

Cemri 等人（MAST 研究團隊）追溯了 1,642 次多 Agent 系統的執行失敗。高達 21.3% 的事故直接源自「驗證缺失（verification gaps）」——即系統直接交付了一個從未經過任何人或程式檢驗的答案。而在剩餘 79% 的各類事故中，常可追溯至「雖然設有檢驗步驟，但檢驗無聲失敗或根本沒有執行」。驗證者是整個架構中真正承重的核心支柱。

PwC 在 2025 年發布的 CrewAI 正式環境部署報告指出：僅僅在系統中補齊結構化的驗證迴圈，就將任務端到端準確率從微不足道的 10% 直接拉升至驚人的 70%。單一角色的引入，換來了 7 倍的巨大效能回報。

### 審查者（Critic）vs 驗證者（Verifier）的本質區別

- 審查者本質上是一個 LLM，負責評估工件的整體品質與設計風格。具有主觀性。極容易被外觀優美、言之鑿鑿的表面包裝所欺騙。
- 驗證者本質上是一段直接運作在工件上的確定性程式。具有客觀性。透過執行結果產出鐵證如山的通過或失敗判定。

兩者必須並存。審查者負責揪出驗證者難以用公式表達的設計品味與架構瑕疵。驗證者則負責精準捕獲審查者在閱讀文字時完全無法察覺、唯有在執行階段才會浮現的細微 bug。

### 致命的反模式（Anti-Pattern）

最常見的災難性反模式：系統中的每一個角色全部由 LLM 擔任，且每個角色的輸出都是客客氣氣的「我看過了，完全沒問題（looks good to me）」。這是 MAST 分類體系中最經典的集體失靈。任何架構中，請務必至少配置一位其通過或失敗判定由程式碼而非 LLM 決定的客觀驗證者。

### 主流框架的實作映射

- **CrewAI**——其 `Agent(role, goal, backstory)` 是角色專門化的教科書式介面。
- **LangGraph**——每個節點皆可配置高度專門化的 prompt；透過圖邊強制約束審查與驗證管線。
- **AutoGen**——在 GroupChat 中使用單詞命名具備特定角色職責的 ConversableAgent。
- **OpenAI Agents SDK**——在不同專業角色的 Agent 之間定義專屬的交接工具。

## Build It｜動手實作

`code/main.py` 實作了一個由四大角色協同編寫 Python 函式的標準管線：

- **規劃者（Planner）** 輸出技術規格。
- **執行者（Executor）** 生成程式碼字串。
- **審查者（Critic）**（模擬 LLM）標註顯而易見的設計瑕疵。
- **驗證者（Verifier）** 在沙盒環境（`exec`）中針對測試案例實際執行生成的程式碼。

展示程式會完整執行兩次對比：第一次是執行者生成正確程式碼的情境（審查者與驗證者皆順利放行）；第二次則是執行者產出不符規格程式碼的情境（審查者因程式碼表面看似合理而產生疏漏，但驗證者透過測試失敗精準攔截）。

執行指令：

```
python3 code/main.py
```

## Use It｜實際應用

`outputs/skill-role-designer.md` 能接收一項業務任務並自動產出完備的角色編制架構（3-5 個角色）、各角色的嚴格輸入／輸出結構描述，以及專屬的客觀驗證者檢查規格。在將各 agent 連線進任何框架之前，務必先使用該工具完成角色架構藍圖。

## Ship It｜交付成果

正式環境上線前的核心自檢清單：

- **至少配備一位確定性的客觀驗證者。** 絕不允許全員皆為純 LLM。
- **每個角色具備明確的 I/O 結構描述。** 規劃者必須回傳結構化規格而非自然語言散文；執行者直接依據該結構描述解析。
- **落實溝通式去幻覺機制。** 執行者在遭遇資訊缺失時必須強制向上游反問；嚴禁私自憑空捏造。
- **審查者與驗證者的嚴格執行順序。** 先跑審查者（成本低廉，快速揪出宏觀設計缺陷），後跑驗證者（耗時較長，精準捕捉執行階段的深層 bug）。
- **嚴格限制修訂迴圈預算。** 審查者與執行者之間的迭代修訂最多允許進行 2 輪，超出後必須果斷上報人工介入。

## Exercises｜練習

1. 執行 `code/main.py` 並仔細觀察驗證者是如何精準揪出審查者所漏掉的潛在 bug。為系統追加一個靜態分析檢查步驟（例如統計 `return` 關鍵字的出現次數）作為輔助驗證者。思考它能捕捉到哪些執行階段測試可能會遺漏的結構問題？
2. 在體系中追加第五個角色：「需求分析師」，負責將使用者的模糊願望轉化為規劃者可直接消費的技術規格。在此架構下，哪些類型的溝通式去幻覺請求應當反向流向該角色？
3. 閱讀 MetaGPT 論文第 3 節（Agents）。整理並列出 MetaGPT 旗下 5 大核心角色各自的標準輸入／輸出結構描述。
4. 閱讀 ChatDev 的對話鏈架構圖（arXiv:2307.07924，圖 3）。具體指出溝通式去幻覺機制在何處成功打破了原本會導致無窮死迴圈的閉環。
5. PwC 報告中 7 倍的準確率躍升主要歸功於驗證迴圈的引入。嘗試設想三種引入客觀驗證者「毫無用武之地」的業務任務——即在此類任務中，對正確性進行確定性檢驗在物理上是不可能的，或成本高昂至不可承受。

## Key Terms｜關鍵術語

| 術語 | 常見說法 | 實際意義 |
|------|----------|----------|
| 角色專門化（Role specialization） | 「不同 agent，各有不同工作」 | 為規劃者、執行者、審查者與驗證者角色調整各自的系統 prompt。 |
| SOP 模式（SOP pattern） | 「編碼進角色的標準作業程序」 | MetaGPT 的架構：為各角色訂定嚴格的輸入／輸出結構描述，讓團隊形成管線。 |
| 溝通式去幻覺（Communicative dehallucination） | 「先詢問，再自行補充」 | ChatDev 模式：細節缺漏時，執行者向規劃者詢問，而不是自行編造。 |
| 審查者（Critic） | 「LLM 審查者」 | 主觀且帶有觀點的審查者，能發現品味問題，但可能被看似合理的文字誤導。 |
| 驗證者（Verifier） | 「確定性檢查」 | 以程式碼判定通過或失敗，例如測試執行器、型別檢查器及結構描述驗證器；無法被話術誤導。 |
| 驗證缺口（Verification gap） | 「沒有人檢查」 | MAST 失敗中占 21.3%；答案交付前沒有進行能抓出錯誤的檢查。 |
| 修訂迴圈（Revision loop） | 「審查者退回修改」 | 審查者拒絕後，執行者根據回饋重新執行；需要設定預算。 |
| 全 LLM 反模式（All-LLM anti-pattern） | 「我看起來覺得沒問題」 | 每個角色都是 LLM，沒有確定性檢查，是典型的 MAST 失敗。 |
