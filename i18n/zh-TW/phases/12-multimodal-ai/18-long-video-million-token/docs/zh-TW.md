# 百萬 Token Context 下的長視訊理解（Long-Video Understanding at Million-Token Context）

> 一段長度為 1 小時、以每秒 24 幀錄製的 4K 影片，經過切片與向量化後，產生的 token 總量高達約 6,000 萬個。一段長達 2 小時的 Podcast 語音轉錄文字僅有 30,000 個 token。即便套用極致激進的空間池化，一部完整的藍光長片依然需要消化數十萬個視覺 token。Google 的 Gemini 1.5（2024 年 3 月）以千萬級（10M）token context 視窗揭開了這個時代的序幕，並在長達數小時的視訊中實現了近乎完美的「大海撈針（Needle-in-a-Haystack）」召回率。LWM（Liu 等人，2024 年 2 月）展示了環形注意力（Ring Attention）的水平擴展路徑；LongVILA 與 Video-XL 進一步推升了長視訊吞吐極限；而 VideoAgent 則開創性地將暴力長視窗替換為 Agent 式的檢索架構。每條技術路徑各自在算力消耗、召回準確度與系統工程難度之間做出了截然不同的抉擇。本課將這幾大流派並排對比、深度剖析。

**Type:** Build
**Languages:** Python (stdlib, needle-in-haystack simulator + agentic-retrieval router)
**Prerequisites:** Phase 12 · 17 (video temporal tokens)
**Time:** ~180 minutes

## Learning Objectives｜學習目標

- 在不同的取樣 FPS 與空間池化倍率下，精確計算超長視訊產生的視覺 token 總消耗量。
- 深入剖析長視訊理解的三大擴展路徑：暴力擴充 context 視窗（Gemini 1.5）、環形分散式注意力（LWM）與特徵壓縮（LongVILA / Video-XL）。
- 在檢索精確度與推論延遲兩大維度上，深入對比原生長視窗 VLM 與基於 Agent 檢索架構的視訊模型（VideoAgent）。
- 為一段 30 分鐘的視訊設計嚴謹的大海撈針（Needle-in-a-Haystack）測試，並量化評估在特定分鐘時間點的檢索召回率。

## The Problem｜問題

在 Qwen2.5-VL 規格下，單一影格在 384 原生解析度下產生約 729 個 patch token。即便套用 3×3 雙線性池化，每幀依然佔用 81 個 token。一段 30 分鐘的短片若以 1 FPS 抽樣，總計 1800 幀 = 145,800 個 token。2025 年代的前沿開源模型能夠勉強塞入，但空間極為吃緊。若將幀率提升至 2 FPS，token 總量暴增至 291,600——只有極少數擁有超巨量視窗的旗艦模型方能承受。

若是一部 2 小時的完整電影，在 1 FPS 下將產生高達 583,000 個 token。這遠超 2026 年多數開源模型的承載上限；必須依賴閉源的 Gemini 2.5 Pro，或在輸入端施加極度激進的二次空間壓縮。

為此，業界分化出了三大核心擴展路徑。

## The Concept｜核心概念

### 路徑一：暴力擴展 Context 視窗（Gemini 1.5、Claude Opus）

最直接的解法：直接以極致的硬體基礎建設強推極限。將模型 context 視窗擴展至數百萬甚至上千萬個 token，在單次前向傳播中吞吐全量資訊。

Gemini 1.5 Pro 率先支援 100 萬 token 視窗；Gemini 1.5 Ultra 擴展至 1,000 萬；到了 2026 年的 Gemini 2.5 Pro，已能游刃有餘地處理長達數小時的超長視訊。其技術報告（arXiv:2403.05530）展示了在接近 950 萬 token 長度下，依然能維持 99.7% 的驚人大海撈針召回率。

背後的工程奧秘：客製化的專有注意力算子實作，搭配先進的階層式記憶體架構（局部注意力 + 全域注意力 + 稀疏注意力），並融合 MoE 專家路由以大幅降低長文字推論運算量。細節未開源，屬商業專利壁壘。

### 路徑二：環形注意力（Ring Attention：LWM、LongVILA）

環形注意力將超長序列切片分散於環狀排列的各個計算裝置中，每台裝置僅維護局部的序列切片。全序列的注意力運算，透過各裝置以環形模式將局部特徵依序傳遞給相鄰節點，邊傳輸邊累加部分注意力結果來完成。

LWM（Liu 等人，2024）藉由這項技術成功訓練出了支援 100 萬 token 視窗的大模型。訓練算力隨序列長度呈「線性」增長，而非傳統注意力機制的二次方爆炸——因為二次方的運算複雜度被均攤至環狀叢集的所有計算節點之中。

LongVILA（arXiv:2408.10188）將該技術移植至多模態 VLM 領域。處理 1400 幀影片、每幀 192 個 token（總長度 26.8 萬 token 的 context），藉由 8 卡平行環形注意力順暢完成預訓練。

### 路徑三：視覺 Token 語意壓縮（Video-XL、LongVA）

相較於暴力擴展視窗，另一種更具性價比的路線是在特徵送入 LLM 之前，先行施加極度激進的語意壓縮。

Video-XL（arXiv:2409.14485）提出了視覺摘要 token 機制：由 N 幀構成的短片段，僅透過交叉注意力濃縮輸出單一「摘要」token。在推論階段，LLM 針對每個短片段僅看見 1 個摘要 token，使全影片的 context 消耗呈指數級暴跌。

LongVA 則藉由「長上下文知識遷移」技術，將 LLM 的 context 支援從 20 萬平滑拉升至 200 萬。先在純文字長文本上訓練，隨後透過共用表徵空間將長上下文能力遷移至視訊端。

特徵壓縮以犧牲「特定時間點微觀像素級細節」為代價，換取了卓越的長程可擴展性。模型能夠精準掌握全片發生的宏觀情節，但有時會漏掉特定某一幀中的微小文字。

### 路徑四：Agent 智慧檢索機制（VideoAgent）

拒絕將整部影片硬塞入 LLM。相反地，將長影片視為外部多模態資料庫，由主控 LLM 透過 Agent 機制按需查詢。

VideoAgent（arXiv:2403.10517）的典型運作流程：

1. LLM 仔細審讀使用者提出的複雜問題。
2. LLM 呼叫專屬的檢索工具，調用相關視訊片段（例如：「找出包含貓咪奔跑的片段區間」）。
3. 工具回傳命中的候選視訊時間戳記。
4. LLM 僅將這幾段短片送入高精度 VLM 中進行局部深度檢索。
5. LLM 綜合資訊生成最終答案，或發起下一步追蹤提問。

這是 LLM 驅動 Agent 範式在超長視訊領域的經典實踐。推論開銷極低（全流程僅對關鍵片段進行特徵編碼），但系統工程架構較為複雜（檢索模組的召回率成為全鏈路的效能瓶頸）。

### 大海撈針基準評測

長上下文多模態評測的黃金標準：在視訊的隨機時間點注入一個獨一無二的視覺或文字標記，隨後要求模型回答必須回憶該標記方能解答的問題。

評測指標：在不同的視訊總長度與標記插入位置下的 Recall@k 召回率。

Gemini 2.5 Pro 在長達 90 分鐘的視訊中依然能維持 >99% 的驚人召回率。開源 72B 旗艦（Qwen2.5-VL-72B、InternVL3-78B）在 30 分鐘長度下維持在 85% 到 90% 區間，而在超過 60 分鐘後開始出現明顯衰退。

而在 2 小時以上的超長片中，若檢索工具素質過硬，VideoAgent 等檢索體系能夠在準確度上打平甚至反超純暴力長視窗模型。

### 技術選型建議

針對 15 分鐘以內的視訊且要求極致精度：選用開源 72B 原生長視窗模型（首選 Qwen2.5-VL-72B）通常足堪勝任。

針對 30 分鐘至 1 小時的視訊內容：開源路線選用 LongVILA 或 Video-XL；若追求商業頂級品質，選用閉源的 Gemini 2.5 Pro。品質標準至關重要——追求極致前沿往往走向閉源。

針對 2 小時以上的長電影或監控全紀錄：果斷選用 VideoAgent 或類似的檢索架構。另一種替代方案是先摘要濃縮為較小片段，再餵入階層式摘要。

### 2026 年正式環境混合架構

在當前的商業正式環境中，超長視訊處理管線普遍演進為混合式架構：

1. 先在全影片上執行低幀率動態 FPS 取樣搭配激進空間池化（建構一個約 10 萬 token 的宏觀全域表徵）。
2. 將全域表徵餵入 72B 級別的 VLM，生成結構化的章節全景大綱與時間軸索引。
3. 當使用者提出特定微觀細節問題時，以該大綱索引為引導，啟動 Agent 檢索機制僅抽取局部高畫質原片進行深度剖析。

這套混合架構完美兼得了暴力長視窗的宏觀把握力與檢索架構的微觀極限解析力。

## Use It｜實際應用

`code/main.py` 完整實作了：

- 涵蓋 1 分鐘至 3 小時超長視訊的動態 token 預算計算器（支援自由配置 FPS 與池化倍率）。
- 視訊大海撈針（Needle-in-a-Haystack）模擬器：在隨機時間戳記注入特徵標記，模擬模型注意力檢索並評估召回率。
- Agent 式視訊檢索路由器原型：模擬依據使用者意圖挑選特定視訊切片餵入下游 VLM 的完整流程。

運行該預算表，直觀感受視訊長度跨越百萬 token 時的震撼算力鴻溝。

## Exercises｜練習

1. 一段 45 分鐘的教學演講影片，在 1 FPS 抽樣且每幀池化為 81 個 token 的設定下，總共會產生多少視覺 token？哪些開源或閉源模型原生具備容納該序列的 context 視窗？

2. 為一段長度為 30 分鐘的視訊設計一份大海撈針評測規格書：你打算在第幾分鐘注入測試標記？其具體的測試提問 prompt 格式為何？

3. 對比暴力長視窗 Qwen2.5-VL-72B（8 萬 token 視窗）與基於檢索的 VideoAgent 架構（Claude 3.5 + 檢索工具）在一條 1 小時影片上的表現。何者在召回率上更勝一籌？何者在推論首字延遲上佔據優勢？

4. 環形注意力（Ring Attention）的記憶體消耗隨序列長度與節點數量呈線性擴展。深入解釋其背後的數學原理，並說明若移除環形輪轉通訊階段會引發何種計算崩潰。

5. 閱讀 Gemini 1.5 論文第 5 節關於大海撈針測試的實測章節。在從 100 萬 token 跨越至 1,000 萬 token 的極限邊界時，模型在特定視訊區間的召回率呈現出何種細微特徵？

## Key Terms｜關鍵術語

| 術語 | 常見俗稱 | 實際意義 |
|------|-----------------|------------------------|
| Brute context | 「暴力硬塞超長視窗」 | 將模型 context 視窗擴展至數百萬甚至千萬級，在單次前向中暴力消化全量輸入 |
| Ring attention | 「環形分散式注意力」 | 將超長序列切片分發至環狀排列的計算裝置，透過非同步特徵輪轉實現線性記憶體擴展 |
| Token compression | 「視覺摘要壓縮 Token」 | 在影格送入 LLM 之前，利用可學習壓縮器將整個短片段濃縮為單一高階摘要 token |
| Needle-in-haystack | 「大海撈針基準測試」 | 在超長輸入的隨機未知位置注入細微標記，檢驗模型是否具備精準定位回憶能力的測試 |
| Agentic retrieval | 「智慧視訊檢索代理」 | 由主控 LLM 擔任規劃大腦，調用專用檢索工具按需定位關鍵片段再進行高畫質深度解析 |
| VideoAgent | 「視訊檢索標準典範」 | 經典的 Agent 視訊檢索架構：「提問分析 → 檢索工具召回 → 片段送入 VLM → 綜合解答」 |
