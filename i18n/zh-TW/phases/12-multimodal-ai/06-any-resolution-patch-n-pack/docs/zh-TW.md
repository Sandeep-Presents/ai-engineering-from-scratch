# 任意解析度視覺：Patch-n'-Pack 與 NaFlex（Any-Resolution Vision: Patch-n'-Pack and NaFlex）

> 現實世界中的影像絕非工整的 224×224 正方形。收據長寬比為 9:16、統計圖表為 16:9、醫療掃描可能高達 4096×4096、手機螢幕截圖則是 9:19.5。2024 年以前 VLM 的粗暴解答——將一切強行縮放為固定正方形——徹底抹殺了讓 OCR、文件理解與高解析度場景解析得以成立的關鍵訊號。Google 的 NaViT（2023）證明了透過區塊對角遮罩（block-diagonal masking），能夠將可變解析度的 patch 打包進單一 Transformer 批次中。Qwen2-VL 的 M-RoPE（2024）則徹底摒棄了絕對位置表。LLaVA-NeXT 的 AnyRes 將高解析度影像切片為全景縮圖與子圖網格。而 SigLIP 2 的 NaFlex 變體（2025）如今已成為希望以單一模型檢查點通吃任意長寬比的開源 VLM 之預設編碼器。本課帶你端到端實作 patch-n'-pack 機制。

**Type:** Build
**Languages:** Python (stdlib, patch packer + block-diagonal mask)
**Prerequisites:** Phase 12 · 01 (ViT patches), Phase 12 · 05 (LLaVA)
**Time:** ~120 minutes

## Learning Objectives｜學習目標

- 將來自不同可變解析度影像批次的 patch 打包至單一連續序列，並建構精確的區塊對角注意力遮罩。
- 針對給定任務，在 AnyRes 切片（LLaVA-NeXT）、NaFlex（SigLIP 2）與 M-RoPE（Qwen2-VL）之間做出最佳技術選型。
- 在不強制縮放變形的前提下，為 OCR、圖表與自然攝影計算合適的 token 預算。
- 指出強制正方形縮放的三大根本缺陷：文字壓扁變形、有效內容遭裁切、以及填充 token 造成的龐大運算浪費。

## The Problem｜問題

Transformer 預期接收一維向量序列。一個批次通常是多個長度相同的序列堆疊而成。若影像全都是 224×224，每一次都能固定切出 196 個 patch token，無需填充（padding），流程順暢。在 224 解析度下訓練、在 224 下推論，開發者再也不必為解析度煩惱。

但真實世界並非如此。文件往往是縱向的肖像比例（8.5×11 英吋，約 2:3）；圖表螢幕截圖多為橫向風景比例（16:9）；發票收據又長又窄（1:3）；醫療斷層掃描則高達 2048×2048 甚至更大；手機螢幕截圖則是狹長的 1170×2532（約 0.46:1）。

2024 年以前的三種主流妥協方案及其失敗原因：

1. 強制縮放為固定正方形（224×224 或 336×336）。非等比擠壓會使文字與人臉嚴重失真；降低解析度則直接破壞圖表標籤與細微 OCR 內容。這是 LLaVA-1.5 之前的標準做法。
2. 裁切為固定長寬比。這會丟棄影像的大部分內容，且如何挑選裁切區域本身就是一個棘手的電腦視覺難題。
3. 等比縮放並以長邊為準進行邊界填充（Pad）。雖然解決了幾何失真，卻使縱向影像高達 50% 以上的 token 被浪費在無意義的填充像素上，且所有這些空白 token 都會帶來二次方的自注意力運算開銷。

2024 至 2025 年的劃時代解法：直接讓 Transformer 依照影像的原生真實解析度消化 patch，並設計精巧的封裝演算法，將長短不一的異質批次無縫打包為單一序列，徹底杜絕無謂的運算浪費。

## The Concept｜核心概念

### NaViT 與 Patch-n'-Pack

NaViT（Dehghani 等人，2023）首次在大規模實踐中驗證了原生動態打包的可行性。其機制非常純粹機械化：

1. 針對批次中的每張影像，依預設的 patch 尺寸（如 14）計算其原生的 patch 網格形狀。
2. 將每張影像的 patch 展平為各自長短不一的一維序列。
3. 將該批次中所有影像的 patch 連續拼接為單一超長序列。
4. 建構區塊對角注意力遮罩（block-diagonal attention mask），確保影像 A 的 patch 僅在影像 A 的內部相互凝視，絕不跨界至影像 B。
5. 為每個 patch 附加空間位置資訊（如 2D RoPE 或分數座標位置 embedding）。

一個包含三張影像的批次——分別為 336×336（576 個 token）、224×224（256 個 token）與 448×336（768 個 token）——會被緊密打包為一個總長 1600 的連續 token 序列，並搭配 1600×1600 的區塊對角遮罩。零填充、零算力浪費，使 Transformer 得以優雅吞吐任意長寬比的視覺輸入。

NaViT 同時引入了訓練期的隨機 patch 丟棄機制（在批次中均勻隨機丟棄 50% 的 patch），既能發揮強大的正則化效果，又能顯著加速預訓練。SigLIP 2 完整繼承了這項優良傳統。

### AnyRes（LLaVA-NeXT）

LLaVA-NeXT 提出的 AnyRes 則是極具工程務實色彩的替代方案。給定一張高解析度影像與一個固定尺寸編碼器（如輸入固定為 336 的 CLIP 或 SigLIP），對影像進行網格切片拼圖：

1. 從預先定義的候選版面中挑選最契合原圖長寬比的網格佈局——例如 (1×1)、(1×2)、(2×1)、(1×3)、(3×1)、(2×2) 等。
2. 將全圖裁切為該網格拼圖；每個拼圖切片皆為獨立的 336×336 區域。
3. 額外產生一張縮圖（thumbnail）：將整張原圖等比縮放為 336×336，作為提供全域視野的背景 token。
4. 將每一個切片與全景縮圖依序餵入凍結的 336 編碼器中，最後將所有切片 token 與縮圖 token 連續拼接。

對於一張 672×672 的影像，若採用 2×2 網格加全景縮圖：總共產生 4 × 576 + 576 = 2880 個視覺 token。代價雖大但成效極佳——LLM 既能細看局部高畫質微觀細節，又能把握宏觀全景。

當你的視覺編碼器完全凍結且天生僅支援單一固定解析度時，AnyRes 是最理想的擴展手段。但面對超大影像時它會引發 token 數量劇烈膨脹（例如 1344×1344 影像在 4×4 網格下會產生 9216 + 576 ≈ 9800 個 token，幾乎能瞬間塞爆 8k 的 LLM context）。

### M-RoPE（Qwen2-VL）

Qwen2-VL 引入了革命性的多模態旋轉位置編碼（Multimodal Rotary Position Embedding, M-RoPE）。它徹底拋棄了 NaViT 的分數位置表與 AnyRes 的切片拼圖概念，直接為每個 patch 賦予三維旋轉座標（時間、高度、寬度）。Query 與 Key 的高維旋轉自然相容於任意的 H、W 與時間序列長度。

M-RoPE 在推論時原生支援任意動態解析度，完全無需為不同尺寸重訓模型。在推論階段傳入任意 H×W 影像，patch 編碼器直接輸出 H/14 × W/14 個 token，每個 token 依據座標取得其 (t=0, r=列, c=行) 的空間座標，RoPE 便能以正確的頻率旋轉注意力。Qwen2.5-VL 與 Qwen3-VL 延續了這項典範；InternVL3 的 V2PE 亦是同類的跨模態變異編碼。

與 AnyRes 相比，M-RoPE 在原生解析度下產生的 token 數嚴格等於 O(H × W / P^2)，沒有切片拼圖帶來的重疊膨脹；但與 NaViT 相比，它在單次前向中依然偏向處理單圖，若想在分散式環境下混合跨解析度批次，外層仍需搭配 patch-n'-pack 進行序列打包。

### NaFlex（SigLIP 2）

NaFlex 是 SigLIP 2 檢查點內建的原生彈性模式。單一模型在推論時能無縫支援多種目標序列長度（如 256、729、1024 個 token）。其內部在訓練時採用 NaViT 風格的 patch-n'-pack 機制，並搭配絕對分數座標位置編碼。其最大賣點在於：單一權重檢查點，在推論時允許開發者依據具體任務自由挑選合適的 token 預算。

對於單純語意任務（分類、跨模態檢索），配置 256 個 token；對於複雜 OCR 或密集圖表理解，則配置 1024 個 token。完全無需重新訓練模型。

### 打包遮罩機制

區塊對角遮罩往往是工程實作中最容易出錯的環節。對於總長度為 `N_total`、涵蓋 `i=0..B-1` 且各影像長度為 `n_i` 的打包序列，形狀為 `(N_total, N_total)` 的注意力遮罩矩陣 `M`，當且僅當兩個索引落在同一張影像所屬的區間塊時值為 1，其餘位置為 0。可藉由累積長度清單高效建構：

```
offsets = [0, n_0, n_0+n_1, ..., N_total]
M[i, j] = 1 iff there exists b where offsets[b] <= i < offsets[b+1] and offsets[b] <= j < offsets[b+1]
```

在 PyTorch 中可利用 `torch.block_diag` 一行完成，亦可透過顯式 gather 建構。而在正式環境中，FlashAttention 的變長序列路徑（`cu_seqlens`）能完全捨棄這張龐大的實體遮罩矩陣，直接利用累積長度張量在序列區間內跳轉運算——對典型批次而言，推論速度比稠密遮罩快約 10 倍。

### Token 預算配置

依據不同業務任務精準規劃 token 策略：

- OCR 與長文件理解：配置 1024 至 4096 個 token。選用 SigLIP 2 NaFlex @ 1024，或 AnyRes 3×3 切片加全景縮圖。
- 統計圖表與 UI 介面截圖：在 384 至 448 原生解析度下配置 729 至 1024 個 token。採用具備像素上限封頂的 Qwen2.5-VL 動態解析度。
- 自然風景與日常生活照片：256 至 576 個 token 足矣。下游 LLM 已經能捕捉充沛語意。請將寶貴的 token 預算花在資訊密度極高的真實內容上。
- 影片理解：空間池化後每幀僅需 64 至 128 個 token，幀率維持在 2 至 8 FPS。第 12.17 課將詳解此主題。

2026 年正式環境的黃金法則：為不同任務設定每張圖的像素上限（max-pixels cap），在上限範圍內維持原生長寬比直接編碼，緊密打包至單一序列，徹底消滅填充浪費。Qwen2.5-VL 專門開放的 `min_pixels` 與 `max_pixels` 參數，正是為這項工程實踐而量身打造。

## Use It｜實際應用

`code/main.py` 為包含整數像素座標的異質影像批次實作了完整的 patch-n'-pack 流程：

- 接收自訂的 (高 H, 寬 W) 影像尺寸清單。
- 在 patch 大小為 14 下精確計算每張影像的 patch 序列長度。
- 將它們打包至總長度為 `sum(n_i)` 的單一連續序列中。
- 建構清晰可視的區塊對角注意力遮罩（為教學清晰起見，採稠密矩陣格式展示）。
- 量化比對緊密打包、正方形填充縮放與 AnyRes 切片拼圖三者的算力開銷差異。
- 印出涵蓋真實異質批次（收據、圖表、手機截圖、生活照）的 token 預算對比表。

運行該程式碼。輸出的一連串對比數字，正是當今所有開源前沿 VLM 全面倒向 patch-n'-pack 的根本原因。

## Ship It｜交付成果

本課產出 `outputs/skill-resolution-budget-planner.md`。給定混合長寬比的工作負載（包含 OCR、圖表、自然照片、視訊影格）以及全域 token 預算上限，它將精確評估並推薦最適策略（NaFlex、AnyRes、M-RoPE 或固定正方形），並為每個請求產生專屬的執行組態參數。在為真實線上產品選型 VLM 時隨時善用此技能——它能防止無謂的 token 數量膨脹破壞服務延遲預算。

## Exercises｜練習

1. 一張長寬為 600×1500（約 1:2.5）的發票收據。在 patch 尺寸為 14 下，原生動態編碼會產生多少個 token？若強制等比縮放填充至 336×336 正方形，又會產生多少 token？在實務中哪一種方式會導致更嚴重的 OCR 辨識率下降？

2. 為包含 4 張影像（長度分別為 256、576、729、1024）的批次建構區塊對角遮罩。驗證注意力矩陣的大小為 2585×2585，且非零項的數量嚴格等於 `256^2 + 576^2 + 729^2 + 1024^2`。

3. 針對一張尺寸為 1792×896 的影像，在 patch 尺寸 14 下對比三種方案：(a) 縮放至 336 後編碼，(b) AnyRes 2×1 切片加縮圖，(c) M-RoPE 原生編碼。何者消耗的 token 總數最少？何者保留了最豐富的幾何細節？

4. 實作隨機 patch 丟棄機制：給定已打包的連續序列，在全序列上均勻隨機丟棄 50% 的 token，並同步更新對應的區塊對角遮罩。測量遮罩稀疏度的變化比例。

5. 閱讀 Qwen2-VL 論文（arXiv:2409.12191）第 3.2 節。以兩句話說明 `min_pixels` 與 `max_pixels` 參數各自調控的邊界，以及為何在實務上兩端皆必須設限。

## Key Terms｜關鍵術語

| 術語 | 常見俗稱 | 實際意義 |
|------|-----------------|------------------------|
| Patch-n'-pack | 「NaViT 風格打包」 | 將來自不同影像的可變長度 patch 序列連續串接至單一批次維度的封裝機制 |
| Block-diagonal mask | 「打包注意力遮罩」 | 限制各影像的 patch 僅能在自身邊界內部進行注意力凝視的區塊對角遮罩矩陣 |
| AnyRes | 「LLaVA-NeXT 網格切片」 | 將高解析度影像切片為固定大小的網格拼圖加全景縮圖，並以固定編碼器逐一切片編碼 |
| NaFlex | 「SigLIP 2 原生彈性解析度」 | SigLIP 2 單一檢查點在推論時原生支援 256/729/1024 多種 token 預算的切換機制 |
| M-RoPE | 「多模態旋轉位置編碼」 | 涵蓋時間、列、行三維度的旋轉位置編碼，無須位置表即可支援任意幾何形狀 |
| cu_seqlens | 「FlashAttention 打包長度」 | FlashAttention 變長路徑使用的累積長度張量，能完全取代實體稠密區塊對角遮罩 |
| min_pixels / max_pixels | 「解析度上下界門檻」 | Qwen2.5-VL 提供的每請求調控參數，用以約束超小或超大輸入時的 token 消耗極限 |
| Visual token budget | 「每張影像的 Token 配額」 | 每張輸入影像最終轉化生成的 patch token 估計數量；決定了 LLM 的輸入開銷與延遲 |
