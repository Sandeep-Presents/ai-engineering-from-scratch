# 基於 HTN 與演化搜尋的規劃架構

> 符號規劃（Symbolic Planning）專職處理那些在構造上必須具備「可證明正確性」的關鍵場景；演化程式碼搜尋（Evolutionary Code Search）則專精於適應度函數（Fitness Function）可被機器客觀檢查的極限最佳化問題。ChatHTN（2025）與 AlphaEvolve（2025）展示了當這兩大流派與大語言模型結合時所釋放出的巨大威力。

**Type:** Build
**Languages:** Python (stdlib)
**Prerequisites:** Phase 14 · 02 (ReWOO and Plan-and-Execute)
**Time:** ~75 minutes

## Learning Objectives｜學習目標

- 深入解釋階層式任務網路（HTN）的核心要素：任務（Tasks）、方法（Methods）、算子（Operators）、前置條件（Preconditions）與效果（Effects）。
- 描述 ChatHTN 的混合協同迴圈——以符號搜尋為主幹，輔以大模型降級拆解。
- 闡明 AlphaEvolve 的演化搜尋閉環，以及為何它必須嚴格依賴可程式化驗證的評估器。
- 以純 Python 標準函式庫實作極簡的 HTN 規劃器與演化搜尋演算法。

## The Problem｜問題

ReWOO（第 2 課）、Plan-and-Execute 與 ReAct 涵蓋了絕大多數常規的 agent 規劃任務。然而，存在兩類它們本質上無法妥善解決的硬核場景：

1. **必須在數學與邏輯上具備可證明正確性的規劃**：排程調度、飛行路徑規劃、法規合規審批流程——整套規劃必須在構造時即確保嚴密無誤。一個語言流暢、但偶爾產生幻覺步驟的大模型規劃在此類場景中是完全無法被接受的。
2. **具備機器可檢查適應度函數的極限最佳化問題**：矩陣乘法演算法改進、資源排程啟發式規則調校、編譯器最佳化 Pass——此時的目標不再是單純「產出一份正確的計畫」，而是「找尋全域最優的計畫」。

HTN 規劃與 AlphaEvolve 正是為解決這兩大異質難題而生。兩者皆將大模型定位為能力的「放大器」，而非盲目放任的替代品。

## The Concept｜核心概念

### 階層式任務網路（HTN）

一個標準的 HTN 包含：

- **任務（Tasks）**：包含待拆解的複合任務（Compound tasks）與可直接執行的基本任務（Primitive tasks）。
- **方法（Methods）**：將複合任務拆解為子任務的具體規則，附帶前置條件。
- **算子（Operators）**：不可分割的原子操作，明確宣告前置條件與執行後對環境造成的狀態效果。
- **狀態（State）**：當前世界的客觀事實集合。

規劃本質：給定目標任務與初始狀態，找尋出一條能將複合任務遞迴拆解為基本算子的路徑，且該算子序列的前置條件在時間軸上依序得到滿足。

HTN 的歷史遠早於現代大語言模型，至今依然是建構「可證明正確性」規劃的權威黃金標準。

### ChatHTN（Gopalakrishnan 等人，2025）

ChatHTN（arXiv:2505.11814）將符號 HTN 搜尋與 LLM 動態查詢深度結合：

1. 嘗試使用現有的已知方法拆解當前的複合任務。
2. 若無任何既有方法適用，向 LLM 提問：「在狀態 `s` 下，你會如何拆解任務 `task`？」
3. 將 LLM 回傳的文字解析為候選子任務清單。
4. 依據算子 Schema 實施嚴格校驗；果斷拒絕非法的拆解方案。
5. 遞迴向下推進。

該論文的核心保證：**產出的每份規劃皆在構造上具備可證明的可靠性**，因為大模型的建議僅被作為「候選拆解方案」輸入系統，絕不可直接肆意竄改底層規劃本身。符號層誓死捍衛正確性；而 LLM 則負責動態擴充方法庫。

線上方法學習（OpenReview `gwYEDY9j2x`，2025 年後續研究）進一步引入了學習器，透過迴歸泛化 LLM 生成的拆解步驟，將 LLM 查詢頻率大幅降低了 75%。

### AlphaEvolve（Novikov 等人，2025）

AlphaEvolve（arXiv:2506.13131，DeepMind，2025 年 6 月）則是另一個完全不同量級的架構神獸：由 Gemini 2.0 Flash/Pro 整合模型所編排的**演化程式碼搜尋引擎**。

執行迴圈：

1. 自一段初始種子程式碼 + 一個程式化評估器（回傳精確的適應度分數）啟動；
2. 由 LLM 整合團隊主動提出程式碼變異提案（Mutations）；
3. 將產生的變異程式碼輸入評估器進行實體運行評分；
4. 保留得分最高的最優候選；發起下一輪突變迭代。

震撼業界的實測戰報：

- 56 年來首次打破 Strassen 演算法紀錄，發現了更快的 4x4 複數矩陣乘法方案（僅需 48 次純量乘法）；
- 透過改良 Borg 叢集排程啟發式演算法，為 Google 基礎設施回收了 0.7% 的龐大算力；
- 在前沿負載上實現了 FlashAttention 32% 的實質執行加速。

強制性的硬約束：**適應度函數必須能被機器確定性、客觀化地快速檢查**。若對自然語言散文進行演化搜尋，系統將徹底發散無法收斂。

### 架構選型決策標準

| 業務問題類別 | 推薦採用方案 | 架構選型根本依據 |
|---|---|---|
| 帶有強硬約束的資源排程 | HTN + ChatHTN | 在邏輯上具備可證明的正確性 |
| 編譯器與演算法最佳化 | AlphaEvolve | 具備機器可程式化驗收的適應度函數 |
| 常規多步驟業務流程執行 | ReAct / ReWOO | 人在迴圈中，無強形式化數學證明需求 |
| 具備單元測試的程式碼重構 | AlphaEvolve | 單元測試套件即天然的評估器 |
| 嚴格受內部安全策略約束的自動化 | HTN | 前置條件能直接對安全策略進行形式化編碼 |

### 典型架構失效模式

- **缺乏算子的虛假 HTN**：若沒有前置條件與狀態效果的嚴密 Schema 定義，所謂「可靠性保證」將瞬間淪為空談。ChatHTN 的「LLM 提議拆解」完全依賴 Schema 來果斷過濾無效動作。
- **缺乏客觀評估器的虛假 AlphaEvolve**：「向大模型詢問這段程式碼是否變得更好」絕非合格的適應度函數！評估器必須具備確定性且運算極其高速。
- **過度設計**：絕大多數常規的 agent 任務根本不需要動用這兩套重型武器。在遇到瓶頸前，始終優先選用簡潔的 ReAct 或 ReWOO。

## Build It｜動手實作

`code/main.py` 以純 Python 標準函式庫實作了兩套教學系統：

- 具備算子、方法、前置條件、效果與 `LLMFallback` 降級機制的標準 HTN 規劃器（當無已知方法匹配時自動觸發降級）。該「LLM」由腳本化的拆解器模擬，確保規劃器能在離線環境下順暢運行。
- 針對算術運算式的演化搜尋器：自動演化出輸出能最小化 `|f(x) - target|` 誤差的數學運算式。評估器具備完全確定性。

運行實驗：

```
python3 code/main.py
```

日誌會清晰展示：HTN 規劃器如何層層拆解複合任務（包含中途觸發的 LLM 降級拆解），以及演化搜尋迴圈如何一步步逼近目標數學運算式。

## Use It｜實際應用

- **HTN 規劃器**：`pyhop`、`SHOP3`，或針對特定垂直領域的安全策略自建規則引擎。
- **ChatHTN**：學術前沿程式碼；其核心模式（符號主幹 + LLM 降級支援）可乾淨移植至任何現代 HTN 規劃器中。
- **AlphaEvolve**：DeepMind 論文；其架構（模型整合突變 + 客觀評估器）具備高度可重現性。開源社群中的 OpenEvolve 等專案正在迅速演進發展。
- **現成 Agent 框架**：目前主流框架尚未原生內建 HTN 或 AlphaEvolve。建議將其封裝為獨立的專業子 agent 或背景批次工作行程。

## Ship It｜交付成果

`outputs/skill-hybrid-planner.md` 能為任何目標環境產出混合規劃器鷹架（支援 HTN 或演化搜尋），並對大模型在系統中所扮演的邊界角色進行嚴格約束。

## Exercises｜練習

1. 為 HTN 規劃器擴充回溯（Backtracking）機制：當某個算子的後置條件在執行時期檢驗失敗時，自動回滾並嘗試下一個替代方法。
2. 為 ChatHTN 實作 LLM 方法快取機制：當 LLM 成功在狀態特徵 `P` 下拆解了任務 `T` 時，持久化儲存該結果。在下次回合中優先檢索方法庫。
3. 將演化搜尋的評估器替換為真實的測試套件。演化出一個能完全通過 20 個測試案例的排序函式；記錄收斂所需的世代數。
4. 研讀 AlphaEvolve 的評估器設計手冊。為你所熟悉的業務領域（SQL 查詢最佳化、測試套件精簡、Kubernetes 部署 YAML 最佳化）設計一套確定性評估器。
5. 綜合架構實踐：利用 HTN 將複合任務拆解為子任務，隨後對每個子任務的基本算子調用演化搜尋進行極致調校。思考該組合在何處大放異彩，在何處存在過度設計？

## Key Terms｜關鍵術語

| 術語 | 常見俗稱 | 實際工程意義 |
|---|---|---|
| HTN | 「階層式規劃器」 | 透過算子、前置條件與狀態效果實施的結構化任務遞迴拆解體系 |
| Method | 「任務拆解規則」 | 將複合任務向下分解為具體子任務的定義途徑 |
| Operator | 「基本原子動作」 | 具備嚴格前置條件與執行效果的實體最小操作單元 |
| ChatHTN | 「LLM + HTN 混合規劃」 | 符號規劃器為主幹，當無已知方法匹配時向 LLM 動態請教拆解建議 |
| AlphaEvolve | 「演化程式碼搜尋」 | 由整合 LLM 提出程式碼變異，由確定性評估器篩選留存的極限最佳化引擎 |
| Fitness function | 「適應度評估器」 | 對產出結果進行評分、可由機器客觀自動化驗證的確定性函式 |
| Online method learning | 「快取 LLM 拆解經驗」 | 持久化儲存並泛化 LLM 產出的規劃規則，大幅削減後續 API 查詢開銷 |
