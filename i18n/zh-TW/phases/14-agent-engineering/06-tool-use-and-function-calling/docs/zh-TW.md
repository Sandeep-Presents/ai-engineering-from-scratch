# 工具使用與函式呼叫

> Toolformer（Schick 等人，2023）開啟了自我監督工具標註的先河。柏克萊函式呼叫排行榜（BFCL V4，Patil 等人，2025）則樹立了 2026 年的業界黃金標準：40% Agentic 自主智能、30% 多回合交談、10% 真實即時評測、10% 靜態評測、10% 幻覺拒答檢測。單回合呼叫已被徹底攻克；而情節記憶、動態決策與長路徑工具呼叫鏈，依然是兵家必爭的深水區。

**Type:** Build
**Languages:** Python (stdlib)
**Prerequisites:** Phase 14 · 01 (Agent Loop), Phase 13 · 01 (Function Calling Deep Dive)
**Time:** ~60 minutes

## Learning Objectives｜學習目標

- 深入闡明 Toolformer 的自我監督訓練信號：唯有當實體執行能有效降低下一個 Token 的預測損失時，才保留該 API 標註。
- 掌握 BFCL V4 的五大評測維度及其各自衡量的核心工程指標。
- 以純 Python 標準函式庫實作一套具備 Schema 校驗、參數型別寬容轉換與執行沙盒隔離的生產級工具註冊表。
- 深度剖析 2026 年的三大未解難題：超長路徑工具鏈、動態即時決策，以及跨回合情節記憶。

## The Problem｜問題

早期的工具使用僅聚焦於：模型能否精確輸出正確的函式呼叫格式？而現代的工具使用則考驗：模型能否跨越 40 個連續步驟、在具備記憶體、部分可觀測、能從工具報錯中自我復原的前提下無縫串聯工具，且絕不無中生有捏造不存在的虛構工具？

Toolformer 確立了技術基準：證明大模型能透過自我監督自主學會何時呼叫工具。BFCL V4 則定義了 2026 年的評測靶標。介於兩者之間的巨大鴻溝，正是所有生產級 agent 必須立足的實戰空間。

## The Concept｜核心概念

### Toolformer（Schick 等人，NeurIPS 2023）

核心思想：讓大模型在自身的預訓練語料庫中主動標註潛在的候選 API 呼叫。對每個候選呼叫進行實體執行。唯有在引入該工具執行結果後、能顯著降低後續 Token 的交叉熵損失時，才正式保留該標註。隨後在該過濾後的語料庫上進行 fine-tuning。

涵蓋工具：計算機、問答系統、搜尋引擎、翻譯器、日曆。此自我監督信號完全基於「該工具能否輔助文本預測」——全程完全不需要任何人工標註資料。

規模效應規律：工具使用能力隨模型規模自然湧現。小型模型引入工具標註反而會損害其原始語言能力；而大型模型則顯著受益。這正是為何 2026 年的前沿旗艦模型原生具備極強的工具呼叫能力，而絕大多數 7B 輕量模型仍需透過專門的工具 fine-tuning 才能穩定運作的根本原因。

### 柏克萊函式呼叫排行榜 V4（Patil 等人，ICML 2025）

BFCL 是 2026 年業界公認的實質評測黃金標準。V4 權重構成：

- **Agentic 自主智能（40%）**：完整的 agent 執行軌跡——考驗記憶、多回合推理與動態決策能力。
- **多回合交談（30%）**：包含工具調用鏈的深層互動對話。
- **真實即時評測（10%）**：來自真實使用者輸入的即時 prompt（難度顯著更高的資料分佈）。
- **靜態評測（10%）**：合成的確定性測試案例。
- **幻覺拒答檢測（10%）**：精準檢測模型在無需調用任何工具時能否果斷拒絕呼叫。

V3 引入了基於真實狀態的評測（State-based Evaluation）：在工具呼叫鏈執行後，直接核驗 API 的真實底層狀態（例如「實體檔案是否已被成功建立？」），而非單純比對 AST 抽象語法樹。V4 則進一步加入了網頁搜尋、記憶體狀態以及對格式敏感度的多維度評測。

2026 年的核心實證發現：單回合函式呼叫已基本被攻克。失效高度集中於情節記憶（跨回合傳遞脈絡）、動態即時決策（依據前次工具結果調整後續工具選取）、超長路徑工具鏈（超過 20 步後開始發生漂移），以及幻覺拒答檢測（在無工具可用時盲目亂呼叫）。

### 工具 Schema 定義

每個供應商皆有自己的格式細節，但底層共享相同的核心骨架：

```
name: string
description: string (what it does, when to use it)
input_schema: JSON Schema (properties, required, types, enums)
```

Anthropic 直接使用 `input_schema`；OpenAI 則使用 `function.parameters`。兩者皆原生支援 JSON Schema 標準。工具描述文字（Description）具備極高的系統權重——模型完全仰賴閱讀這些描述來挑選正確的工具。糟糕模糊的工具描述，是導致「模型選錯工具」的頭號頭號元兇。

### 參數二次校驗與防禦

切勿盲目信任模型發出的任何工具呼叫。在執行前必須強制實施：

1. **型別寬容轉換（Type coercion）**：模型在 Schema 宣告為 int 時可能回傳字串 "5"。在無歧義時進行安全自動轉型；在存在模糊性時果斷拒絕。
2. **列舉值檢查（Enum validation）**：若 Schema 宣告 `status in {"open", "closed"}` 而模型發送了 `"in_progress"`，以具備指導意義的清晰錯誤明確拒絕。
3. **必填欄位核對**：缺失必填欄位時，立刻向模型回傳結構化的錯誤觀察字串，絕不可引發底層行程崩潰。
4. **格式嚴格校驗**：針對日期、電子郵件、URL——使用實體剖析器進行語法驗證，切勿單純依賴脆弱的正則表達式。

每次校驗失敗皆應封裝為結構化的環境觀察反饋給模型，賦予模型在下次回合以正確格式自我修復重試的機會。

### 並行工具呼叫（Parallel Tool Calls）

現代模型支援在單次 Assistant 回合中並行輸出多個工具呼叫。處理流程：

1. 模型發送 3 個工具呼叫，各自附帶唯一的 `tool_use_id`。
2. 執行時期並行分派執行（若彼此互不相依）。
3. 每個執行結果皆作為獨立的 `tool_result` 區塊回傳，並透過 `tool_use_id` 嚴格精確關聯。

關鍵工程原則：將關聯識別碼視為不可動搖的生命線。一旦順序錯位，會引發「將工具 A 的結果餵給工具 B」的災難性錯位。

### 沙盒隔離邊界（Sandboxing）

工具實體執行處正是系統最關鍵的沙盒邊界。詳見第 09 課深入解析。核心原則：每項工具皆應明確宣告其讀寫範圍、網路存取權限、執行超時時間與記憶體上限。通用的 `run_shell(cmd)` 屬於高危險警訊；職責單一的高精度工具（如 `git_status()`）才具備實質安全性。

## Build It｜動手實作

`code/main.py` 以純 Python 標準函式庫實作了一套生產級工具註冊表：

- 輕量 JSON Schema 子集校驗器；
- 支援宣告功能描述、輸入 Schema、執行超時與實體執行常式的工具註冊機制；
- 參數自動轉型與 enum 列舉值檢查；
- 具備關聯識別碼的並行工具分派器；
- 將錯誤觀察封裝為結構化字串回饋。

運行實驗：

```
python3 code/main.py
```

輸出演示了一個迷你 agent 在單次回合中同時呼叫三個工具，其中包含一個刻意格式畸形的呼叫被精準攔截，並回傳了具備指引性的結構化錯誤，讓模型得以據此自我修正。

## Use It｜實際應用

各供應商皆維護專屬的工具 Schema——Anthropic、OpenAI、Gemini、Bedrock。若需跨多供應商部署，請引入抽象轉譯層（OpenAI Agents SDK、Vercel AI SDK、LangChain 工具適配器）。BFCL 是業界公認的權威基準線——若工具呼叫是你產品的核心支柱，在正式發布前務必將你的 agent 接入 BFCL 進行完整基準評測。

## Ship It｜交付成果

`outputs/skill-tool-registry.md` 能為特定業務領域自動產出合規的工具目錄、Schema 定義與註冊表骨架。內建描述文字品質檢查清單（確保每個工具的描述皆明確告知模型何時應當選用它）。

## Exercises｜練習

1. 新增一個「No-op 空操作」工具，賦予模型在無合適工具時顯式宣告放棄調用的能力。在類似 BFCL 的幻覺拒答測試集上實測其準確率變化。
2. 為整數字串與浮點數字串實作自動型別轉型。在何種臨界情境下，這種寬容轉型反而會暗中掩蓋真實的程式錯誤？
3. 為每個工具新增獨立的超時定時器與斷路器機制（熔斷器：連續 3 次失敗後自動暫停該工具 60 秒）。這對模型的錯誤復原行為產生了何種影響？
4. 研讀 BFCL V4 官方文件。挑選其中一個評測維度（例如「多回合交談」），將 10 個範例 prompt 輸入你的 agent，並統計通過率。
5. 將此教學校驗器改寫為 Pydantic 或 Zod 實作。深入分析 Pydantic/Zod 成功捕捉到了哪些玩具校驗器所遺漏的極端邊界問題？

## Key Terms｜關鍵術語

| 術語 | 常見俗稱 | 實際工程意義 |
|---|---|---|
| Function calling | 「工具使用」 | 依據已校驗的 Schema 所實施的結構化輸出工具調用機制 |
| Toolformer | 「自我監督工具標註」 | Schick 等人 2023 年提出——保留能實質降低下一個 Token 損失的工具呼叫 |
| BFCL | 「柏克萊函式呼叫排行榜」 | 2026 年標準基準：40% Agentic、30% 多回合、10% 即時、10% 靜態、10% 幻覺拒答 |
| Tool schema | 「面向模型的函式簽名」 | 包含名稱、描述以及參數之 JSON Schema 的規格宣告 |
| tool_use_id | 「關聯識別碼」 | 負責將單次工具呼叫與其非同步回傳結果精確綁定的關鍵 ID；並行分派必備 |
| Hallucination detection | 「知道何時不呼叫」 | BFCL V4 核心維度：在無合適工具可解決問題時果斷拒絕盲目調用 |
| Argument coercion | 「字串自動轉整數」 | 針對可預測的格式輕微錯位實施的窄範圍容錯；存在歧義時堅決拒絕 |
| Sandboxing | 「工具執行隔離邊界」 | 為每項工具獨立配置的檔案讀寫範疇、網路存取、逾時限制與記憶體配額 |
