# MCP 可靠性、取消機制與流量控制

> 請求 ID 僅能關聯訊息；它無法讓實質副作用天然具備安全性、無法強制中止背景工作行程，亦無法防止慢速消費者拖垮串流傳輸。

**Type:** Build
**Languages:** Python
**Prerequisites:** Phase 13, Lessons 09 and 13
**Time:** ~120 minutes

## Learning Objectives｜學習目標

- 針對 stdio 與 Streamable HTTP 正確分別實作其標準的取消信號。
- 妥善解決完成與取消之間的競態條件，確保在取消確立後絕不發送殘留訊息。
- 嚴格區分瞬時請求取消與持久化 `tasks/cancel` 的語義邊界。
- 依據操作副作用與顯式冪等鍵（Idempotency Keys）制定重試決策。
- 為進度推播佇列設定容量上限，同時保證最終 JSON-RPC 回應絕不遺失。
- 透過重新連線、權威重新拉取與帶有抖動的指數退避，實現串流的彈性復原。

## The Problem｜問題

平順的理想路徑（Happy Path）往往掩蓋了分散式系統中最昂貴的架構缺陷。

想像一個情境：用戶端呼叫一項工具，伺服器開始背景運算，進度事件依序傳遞，但中繼反向代理伺服器卻在緩衝區中堆積串流；用戶端達到逾時時間並斷開連線；伺服器剛好在一毫秒之後執行完成；用戶端隨後帶著全新的 JSON-RPC 請求 ID 發起重試；於是該項具備副作用的狀態變更被重複執行了兩次。

鏈路中的每個元件各自的本機行為看似完全合規，但整個系統全域卻徹底崩潰。

MCP 規範了標準的訊息格式與傳輸層行為，但你的應用程式依然必須全權承擔以下核心架構決策：

- 執行時間預算；
- 業務層級的冪等性保證；
- 有界限的緩衝佇列；
- 失敗重試的風險分類；
- 持久化長任務的狀態維護；
- 重新連線與重新拉取的系統策略。

本課將在確定性的模擬環境中親手建置這些關鍵決策。全流程不依賴任何人工 sleep 延遲、實體網路 Socket 或隨機故障。你能直接精確控制取消事件的發生順序。其中一項同步執行緒測試將強制兩個帳本用戶端針對同一個冪等鍵發起激烈的並發競爭。

## Request Cancellation Is Transport-Specific｜請求取消機制取決於傳輸模式

各傳輸層的業務意圖完全一致：用戶端不再需要該次正在傳輸中的執行結果。然而，線路傳輸上的具體信號卻截然不同。

### stdio

stdio 傳輸模式採用單一共享的雙向通訊通道。用戶端對外發送標準通知：

```json
{
  "jsonrpc": "2.0",
  "method": "notifications/cancelled",
  "params": {
    "requestId": 41,
    "reason": "User closed the operation"
  }
}
```

該通知屬於單向發後不理（Fire-and-forget）。伺服器絕不可針對該通知回傳任何 JSON-RPC 回應。

伺服器應當主動停止工作、釋放相關資源，並避免為已被取消的請求發送後續回應。當請求 ID 未知、已經執行完成，或在技術上無法安全中止時，伺服器可選擇略過該取消通知。

遇到格式損壞、未知 ID 或已完成的取消通知時，伺服器一律予以靜默略過。若將這些不可避免的競態條件轉換為全新的系統錯誤，只會引發更多無休止的次生競態。

### Streamable HTTP

現代 Streamable HTTP 為每個請求指派獨立的專屬 HTTP 回應連線或 SSE 回應串流。用戶端透過**直接關閉該請求的底層回應串流**來傳達取消信號。

**絕不可**針對常規的 HTTP 請求透過 POST 發送 `notifications/cancelled`！直接關閉連線串流本身就是法定的取消信號。

一旦伺服器檢測到 HTTP 斷開連線，應當立刻停止背景工作，且絕不可再為該請求發送任何後續訊息。

### 伺服器端發起的取消範疇極為狹窄

伺服器端絕不可使用 `notifications/cancelled` 來隨意取消任意用戶端呼叫。在 stdio 模式下，伺服器端主動發送的取消信號嚴格僅保留用於終止 `subscriptions/listen` 訂閱請求。切勿將此路徑與常規的用戶端請求取消混為一談。

## Cancellation Is a Race｜取消本質上是一場競態競爭

事件發生的先後順序存在兩種完全合法的結果：

### 取消勝出（Cancellation wins）

```text
request starts
client sends cancellation signal
server marks request cancelled
worker reaches completion
server suppresses the response
```

### 完成勝出（Completion wins）

```text
request starts
worker commits the result
server sends the response
cancellation arrives late
server ignores the late notification
```

用戶端亦必須主動略過任何針對其已放棄之請求所姍姍遲到的逾期回應。由於網路延遲的存在，通訊兩端皆無法證明對方究竟是在哪個精確時刻最先觀察到特定事件。

```figure
mcp-reliability-race
```

本課的 `RequestCoordinator` 為每個請求維護單一不可變的終態。在取消確立後，`complete()` 絕不輸出任何回應；遲到的取消通知亦無法竄改已標記為完成的記錄。

## Timeouts Need Two Clocks｜逾時控制需要雙時鐘防線

單純依賴單一靜態的閒置定時器是遠遠不夠的。

必須同時設定兩大上限：

1. **閒置逾時（Idle timeout）**：允許請求在無任何有效產出活動下維持存活的最大時限。
2. **最大絕對逾時（Maximum timeout）**：自請求啟動當下起算、以實體掛鐘時間為準的絕對時限上限。

接收到進度推播可以重設閒置時鐘，但**絕不可延長或重設最大絕對時限**！

```text
start: 0 ms
progress: 400 ms
progress: 800 ms
progress: 1200 ms
idle timeout: 500 ms
maximum timeout: 2000 ms
```

在 1500 ms 時，該請求依然維持活躍，因為最新一次進度回報發生於 300 ms 之前。然而在抵達 2000 ms 瞬間，最大絕對時限會強制將其取消，即使在 1999 ms 時恰好抵達了另一筆進度事件亦不例外。

進度推播本身是選填的。伺服器可以接收進度 Token 卻不發送任何更新通知。切勿單純因傳入了進度 Token 就將其轉化為無限期等待的死循環。

MCP 的進度數值必須單調遞增。所有進度通知在任務完成或取消後必須立刻停止。伺服器必須對進度推播實施頻率限制，防止高效背景工作行程淹沒傳輸層。

## 請求取消絕非 `tasks/cancel`

這兩項機制解決的是生命週期截然不同的架構問題：

| 機制 | 作用目標 | 傳輸信號 | 成功意味著何種狀態 |
|---|---|---|---|
| stdio 請求取消 | 單次正在傳輸中的 RPC 呼叫 | `notifications/cancelled` | 用戶端已放棄該次請求；伺服器若可行應停止運算 |
| HTTP 請求取消 | 單次正在傳輸中的回應串流 | 關閉底層串流連線 | 用戶端已放棄該次請求；伺服器若可行應停止運算 |
| `tasks/cancel` | 一項持久化的長任務 Task | 常規的 MCP 請求 | 伺服器已正式確認接收到了使用者的取消意圖 |

`tasks/cancel` 的成功回應，完全無法證明背景工作行程已經實質停止。該任務可能會持續保持在 `working` 狀態，直到背景行程抵達下一個檢查點並檢查該旗標為止；運算甚至可能搶在該檢查點前夕提前執行完畢。

當底層 HTTP 連線意外斷開時，**切勿刪除持久化 Task 的狀態**！建立 Task 的初衷，正是為了讓其生命週期能夠超越單次請求與單次實體連線的存續時間。

## A New JSON-RPC ID Is Not Idempotency｜全新的 JSON-RPC ID 絕非冪等性保證

JSON-RPC 訊息 ID 僅用於在通訊層面關聯請求與回應，它完全無法標識業務層級的實體操作。

假設用戶端發起一筆扣款請求（ID 為 `41`），因網路連線中斷遺失了回應，隨後攜帶全新的 ID `42` 發起重試。在伺服器眼中，這是兩則互不相干的獨立訊息。若缺乏業務層級的唯一鍵值，伺服器根本無從知曉這兩次請求代表的是同一次結帳購物。

冪等鍵負責唯一標識業務意圖：

```json
{
  "name": "charge_account",
  "arguments": {
    "account": "acct-7",
    "cents": 1200,
    "idempotencyKey": "checkout-7"
  }
}
```

伺服器持久化儲存：

- 冪等鍵；
- 操作輸入參數的特徵指紋；
- 已成功確認寫入的執行結果。

攜帶完全相同的鍵值與完全相同的參數時，伺服器直接回傳預存的結果；但若相同的鍵值伴隨了不同的參數，伺服器必須堅決予以拒絕。這能徹底防止因意外重用鍵值而覆寫篡改了不同的業務操作。

### 帳本邊界必須具備原子性與持久化保證

以下執行順序存在嚴重的競態漏洞：

```text
check key
run mutation
store result
```

兩個並發工作者可能同時判定鍵值不存在，進而各自重複執行了兩次實質變更。在副作用已發生、但結果尚未寫入資料庫之前遭遇系統崩潰，同樣會在後續重試時引發嚴重的狀態歧義。

本課採用基於實體檔案的 SQLite 帳本。透過 `BEGIN IMMEDIATE` 事務，將鍵值存在性檢查、模擬業務副作用、執行計數器累加與結果寫入原子封裝於單一資料庫事務中。兩個並發連線針對同一個鍵展開競爭時，能確鑿保證僅產生一次業務執行與一次結果確認。關閉並重新開啟資料庫，該記錄依然完好如初。

所有的回傳數值皆自持久化 JSON 資料重新建構。呼叫端絕不會取得帳本內部所持有的可變物件，因此外部對回傳字典的就地修改完全無法污染後續的重放結果。

本教學模擬器中的業務副作用是事務內部的回執與計數器。在真實生產實踐中，單純寫入本地資料表無法使外部信用卡扣款、叢集部署或第三方 API 呼叫天然具備原子性。正式環境必須依賴持久化的分散式資料庫事務、交易收件匣（Transactional Outbox），或仰賴外部供應商原生支援相同的冪等鍵機制。單靠行程記憶體鎖無法跨多個實體複本提供保護，更無法在重啟後倖存。

### 重試決策分類矩陣

在實作任何重試機制前，必須先嚴格分類業務操作：

| 操作分類 | 典型範例 | 重試策略原則 |
|---|---|---|
| 安全操作（Safe） | 無副作用的確定性讀取操作 | 在釐清具體失敗邊界後，攜帶全新的 JSON-RPC ID 放心重試 |
| 條件式安全（Conditional） | 具備持久化冪等鍵的狀態變更操作 | 攜帶完全相同的冪等鍵與完全相同的參數發起重試 |
| 不安全操作（Unsafe） | 缺乏業務去重機制的狀態變更操作 | 嚴禁自動重試！必須先進行人工或系統對帳調解 |

工具描述元中宣告的 `readOnlyHint` 與 `idempotentHint` 僅屬於未經審查的提示。重試的安全性完全取決於應用程式契約與伺服器端的實體實作。

## Backpressure Is Part of Correctness｜背壓控制是系統正確性不可分割的一環

SSE 生產者產出進度事件的速度，可能遠高於用戶端、反向代理或底層網路的消費能力。毫無上限的記憶體佇列會將單純的連線慢速惡化為嚴重的記憶體耗盡（OOM）。

必須使用具備容量配額的有界緩衝佇列，並清晰定義在超載時哪些資料允許被捨棄。

進度事件是可替換的：同一 Token 的最新進度數值會自動覆寫先前的舊數值。但最終的 JSON-RPC 業務回應**絕不可被捨棄**！

本課緩衝區實施以下處置策略：

1. 自動合併同一 Token 的相鄰進度通知；
2. 當達到佇列容量上限時，優先丟棄最舊的進度事件；
3. 將該串流標記為「需要權威重新拉取狀態」；
4. 始終保留最終的 JSON-RPC 回應；
5. 堅決拒絕會導致必須捨棄另一筆最終回應的超載狀態。

這是伴隨明確復原方案的受控丟包。默默假裝一切正常的靜默丟失絕非合格的工程策略。

### 反向代理快取與緩衝干擾

伺服器端可能正在平滑串流輸出，而中間的反向代理伺服器卻在本地緩衝區中悄悄扣押所有事件。

針對 SSE 回應，必須發布以下 HTTP 標頭：

```http
Content-Type: text/event-stream
Cache-Control: no-cache
X-Accel-Buffering: no
```

2026 年的 Streamable HTTP 規範強烈推薦宣告 `X-Accel-Buffering: no`，以確保相容的反向代理伺服器（如 Nginx）能即時向下游透傳每個事件。

針對長時間處於安靜狀態的長連線，定期發送 SSE 註解行：

```text
:
```

用戶端會主動略過所有以冒號開頭的註解行。然而中繼節點能因此看見持續的保活流量，大幅降低因判定閒置而擅自中斷連線的機率。

保活心跳絕非業務進度。切勿單純因為收到傳輸層心跳註解，就擅自重試或延長業務層級的閒置逾時時鐘。

## Reconnect Means Refetch｜重新連線意味著必須重新拉取

現代 Streamable HTTP **完全不支援**透過 `Last-Event-ID` 實現中斷續傳的 SSE 機制。

當 `subscriptions/listen` 串流發生連線中斷後：

1. 發起全新的監聽請求，並攜帶全新的 JSON-RPC ID；
2. 重新註冊所需的訂閱過濾器；
3. 透過官方權威端點主動重新拉取受影響的工具、資源、Prompt 或 Tasks 狀態；
4. 利用穩定的實體 ID 對應用程式本機狀態進行去重整合；
5. 絕不可單純因為先前的回應遺失，就盲目重放具備副作用的不安全變更操作。

本課的故障復原方案明確將 `sendLastEventId` 配置為 false，並清晰列舉了斷線後必須重新拉取的權威資源清單。

### 防範驚群效應（Reconnect Herd）

若 10,000 個並發用戶端在斷線後恰好於第 1.0 秒整同時發起重新連線，剛經歷重啟的伺服器將被瞬間再次擊垮。

必須採用帶有隨機抖動（Jitter）與最大上限的指數退避演算法（Exponential Backoff）。本課透過用戶端 ID 與重試輪次計算確定性的偽隨機抖動，確保單元測試具備百分之百的可重複性：

```text
attempt 0: up to 250 ms
attempt 1: up to 500 ms
attempt 2: up to 1000 ms
...
cap: 8000 ms
```

正式環境可使用密碼學安全隨機數或執行時期隨機函式。其核心不變量在於分散重試時間點，而非具體數學公式。

## Build It｜動手實作

`code/main.py` 實作了五套高可靠性核心元件：

### `RequestCoordinator`

- 啟動傳輸中請求，並嚴格套用閒置與最大絕對雙逾時防線；
- 發布單調遞增的進度通知；
- 針對 stdio 與 HTTP 分別產出正確的底層取消信號；
- 靜默略過非法的取消通知；
- 明確處理取消與完成之間的終態競爭；
- 將伺服器端主動發起的取消嚴格限制於 stdio 訂閱情境。

### `MutationLedger`

- 確鑿證明在缺乏業務冪等鍵時，兩個不同的 JSON-RPC ID 會導致操作被重複執行兩次；
- 運用基於實體檔案的 SQLite 事務原子完成鍵值檢查、副作用模擬、
  計數器累加與結果確認寫入；
- 跨獨立的資料庫連線，為相同冪等鍵與相同參數
  進行精確去重；
- 果斷拒絕攜帶不同參數重用同一冪等鍵的違規請求；
- 始終回傳防禦性複本，並在資料庫關閉後重新開啟時依然完好保留寫入記錄。

### `DurableTaskService`

- 正式確認接收取消請求（Ack）；
- 將任務維持在 `working` 狀態，直到背景工作行程抵達檢查點；
- 具象化演示為何接收取消請求絕不等於任務已終止。

### `BoundedSseBuffer`

- 在高負載下自動合併或受控丟棄進度事件；
- 明確記錄該串流後續需要實施權威重新拉取；
- 誓死捍衛最終的 JSON-RPC 業務回應絕不被丟棄。

### 復原輔助常式

- 產出防範反向代理緩衝的標準 SSE 標頭與保活註解行；
- 建立連線重建與狀態重新拉取計畫；
- 透過確定性的指數退避與隨機抖動分散重試連線峰值。

## Interactive Lab｜互動實驗

在不引入任何人工延遲的前提下，實測四種事件發生順序：

1. 啟動請求 `A`，將其取消，隨後調用 `complete()`。
2. 啟動請求 `B`，順利完成它，隨後傳入取消信號。
3. 啟動請求 `C`，在每次閒置逾時前夕發布進度更新，隨後跨越最大絕對逾時線。
4. 透過 Streamable HTTP 啟動請求 `D`，並手動關閉其回應串流。

記錄每種情境下的關鍵項目：

- 請求的最終終態；
- 最終業務回應是否存在；
- 實際發布至實體線路上的取消信號；
- 用戶端應當主動忽略的事件。

隨後將情境 `D` 切換為 stdio 模式。業務操作完全相同，但實體線路上的取消信號必須精確切換。

## Practice Lab｜實戰實驗

為 `MutationLedger` 擴充一套 `reserve_inventory` 庫存保留變更操作。

具體需求：

1. 冪等鍵嚴格綁定 SKU、數量、租戶與操作名稱。
2. 攜帶完全相同的鍵值與參數重試時，直接回傳初次的庫存保留結果。
3. 攜帶變更後的數量發起重試時直接報錯，且絕不建立第二次庫存保留。
4. 已成功確認寫入但遺失回應的執行，能透過冪等鍵重新對帳復原。
5. 回傳結果中絕不洩漏機密或支付資料。
6. 當用戶端未提供冪等鍵時，自動停用重試機制。
7. 模擬訂閱中斷情境，在決定下一步行動前主動重新拉取庫存記錄。
8. 讓兩個帳本連線在同步屏障（Barrier）處就緒，並並發發送完全相同的冪等鍵。
   斷言實質上僅成功確認寫入了一次庫存保留。
9. 故意修改初次取得的庫存保留回傳物件。重新重放該鍵值，證明
   底層儲存的原始結果完全未遭竄改。
10. 關閉並重新開啟實體帳本檔案，隨後透過鍵值順利復原庫存記錄。

請保持實驗的嚴謹性：若庫存資料實際上位於外部微服務中，深入解釋該遠端服務是否原生支援相同的冪等鍵，或者是否需要引入交易收件匣（Transactional Outbox）來跨越本地交易確認與遠端副作用的邊界。

## Shipped Artifact｜交付產物

`outputs/skill-mcp-reliability-reviewer.md` 是一套專門審查可靠性的實用 skill。傳入 MCP 操作、傳輸模式、逾時策略、重試邏輯、佇列限制與復原規劃，它能自動產出競態分析表、重試分類建議、冪等性邊界設計、流量控制檢查清單與故障注入測試資料。

## Verify It｜成果驗證

當以下條件全數滿足時，代表本課實作圓滿達標：

- stdio 模式下的取消發送 `notifications/cancelled` 且不接收任何回應。
- Streamable HTTP 模式下的取消直接關閉請求串流，且絕不發送取消 POST。
- 「取消先於完成」時，最終回應被完全抑制不發送。
- 「完成先於取消」時，保留正常業務回應，並安全略過遲到的取消通知。
- 進度推播能重設閒置逾時，但絕無法重設或突破最大絕對逾時上限。
- 單純使用全新的 JSON-RPC ID 會導致狀態變更操作被重複執行兩次。
- 單一冪等鍵搭配完全相同的參數，在雙連線並發激烈競爭下
  嚴格僅實質執行一次。
- 已確認寫入的記錄在資料庫關閉重啟後依然完好存在，重放時回傳防禦性複本。
- 修改回傳的結果物件，完全無法影響資料庫內部預存的真實結果。
- 有界緩衝區嚴格維持在容量上限之內，且誓死捍衛最終業務回應不被捨棄。
- 重新連線使用全新請求 ID、絕不發送 `Last-Event-ID`，並主動重新拉取受影響的狀態。
- `tasks/cancel` 的確認接收使任務維持在非終態，直到背景工作者實質檢測到該狀態為止。

## Production Failure Modes｜正式環境失效模式

| 失效情境 | 開發者觀察到的表象 | 正確架構處置準則 |
|---|---|---|
| HTTP 用戶端錯誤發送取消 POST | 伺服器與用戶端對請求存續狀態產生嚴重分歧 | 嚴格透過關閉該請求的 SSE 回應串流發送取消信號 |
| 取消確立後伺服器依然輸出回應 | 用戶端收到了已無意義且無法處理的逾期殘留結果 | 取消勝出時立刻停止運算，並堅決壓制後續訊息發送 |
| 進度推播無限制重設所有定時器 | 卡死或無窮迴圈的任務在系統中長生不老 | 維護獨立且不可突破的絕對最大逾時上限 |
| 將全新 RPC ID 誤當作業務去重 | 重複扣款、重複部署或重複刪除事故頻發 | 引入具備業務語義的持久化應用層冪等鍵 |
| 鍵值檢查與實質執行未原子綁定 | 並發工作者同時判定鍵值缺失，導致重複執行 | 透過資料庫事務將鍵值占用、副作用記錄與結果確認原子鎖定 |
| 跨叢集複本使用純記憶體帳本 | 伺服器重啟或其他 Pod 完全遺忘了先前的寫入 | 採用持久化共享儲存或由上游供應商保證冪等性 |
| 直接回傳儲存的可變結果字典 | 呼叫端的就地修改暗中污染了後續其他重放結果 | 序列化已確認寫入的結果，回傳時始終提供深層防禦性複本 |
| 相同鍵值伴隨變更後的參數重用 | 單一冪等鍵被錯誤指派給兩筆完全不同的業務操作 | 計算並嚴格比對輸入參數的特徵指紋 |
| 無界限進度推播佇列 | 面對慢速消費者時記憶體飆升引發 OOM 崩潰 | 在容量上限內自動合併並主動丟棄可替換的舊進度事件 |
| 超載壓力下捨棄了最終回應 | 用戶端永遠無法得知該次請求的最終業務成敗 | 嚴格預留空間或淘汰進度事件，誓死捍衛最終回應 |
| 反向代理悄悄緩衝 SSE 事件 | 進度事件成批突發抵達，或在逾時中斷後才噴出 | 停用反向代理緩衝並配置相容的代理逾時參數 |
| 錯誤假設支援 `Last-Event-ID` | 用戶端企圖自伺服器根本不支援的狀態中復原 | 攜帶全新請求 ID 重新連線，並主動權威重新拉取狀態 |
| 海量用戶端斷線後同時重連 | 伺服器剛重啟便遭遇驚群效應瞬間再次癱瘓 | 採用帶有隨機抖動與最大上限的指數退避重試 |
| 將 Task 取消確認誤當作已終止 | UI 顯示已停止，但背景行程依然在持續耗能運算 | 持續輪詢 Task 狀態，直到其狀態碼正式抵達終態 |

## Capstone Connection｜總結專題關聯

工具生態系總結專題應當將系統可靠性視為可執行的具體測試證據，而非架構圖上的一段客套話。

總結專題必須交付以下關鍵憑證：

- 針對每種傳輸模式各提供一份取消競態分析日誌；
- 為所有具備副作用的操作提供重試決策表；
- 冪等鍵儲存紀錄與參數不符時的防禦測試資料；
- 雙連線並發競爭日誌、重啟校驗紀錄與變更別名測試資料；
- 有界緩衝區超載壓力測試結果；
- 反向代理標準 SSE 標頭與閒置保活策略；
- 詳列權威重新拉取端點的重新連線復原計畫；
- 包含持久化 Task 取消歷程的完整執行日誌（若專題使用 Tasks）。

在本地單一行程中跑通一條順暢的請求，僅能證明最理想路徑。唯有當遺失回應、遲到取消、慢速連線與重連驚群皆具備確定性的架構處置時，系統才算真正具備進入正式環境的生產就緒度。

## Key Terms｜關鍵術語

| 術語 | 實際工程意義 |
|---|---|
| Request cancellation | 主動放棄單次正在傳輸中、尚未完成的瞬時 MCP 請求 |
| Cancellation race | 終態完成事件與取消信號在微秒維度下的先後競爭條件 |
| Idle timeout | 自上一次有效請求活動發生起算所允許的閒置時間上限 |
| Maximum timeout | 自請求發起當下起算的絕對時間上限，完全不受進度更新影響 |
| Idempotency key | 負責跨多次重試唯一標識單一業務意圖的應用層唯一識別碼 |
| Atomic ledger | 將鍵值宣告、副作用記錄與結果確認作為不可分割單元寫入的持久化帳本 |
| Backpressure | 當生產者產出速率超越消費者處理能力時所實施的流量抑制保護 |
| Progress coalescing | 自動使用最新進度數值覆寫取代先前未及傳輸的舊有進度資料 |
| Refetch | 串流發生中斷後，主動透過權威端點重新讀取完整現狀狀態 |
| Jitter | 故意在重試間隔中引入的隨機分佈偏差，用以將請求平滑分散至時間軸 |
