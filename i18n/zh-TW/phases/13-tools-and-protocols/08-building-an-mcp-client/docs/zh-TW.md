# 打造 MCP 用戶端：服務發現、路由轉發與雙時代降級相容（Building an MCP Client: Discovery, Routing, and Dual-Era Fallback）

> 現代 MCP 用戶端在每次發起請求時，皆重複宣告其協定契約。其面臨的最嚴峻相容性抉擇，在於如何精準研判一個舊伺服器究竟是真實的傳統版本，還是某個正在回報可修復錯誤的現代伺服器。

**Type:** Build
**Languages:** Python
**Prerequisites:** Phase 13, Lesson 07
**Time:** ~85 minutes

## Learning Objectives｜學習目標

- 為發起的每一個 MCP `2026-07-28` 請求，組裝包含最新後設資料的完整負載。
- 利用 `server/discover` 探測 stdio 伺服器，並智慧協商出雙方共同支援的現代最高版本。
- 僅對被顯式列入允許清單（Allowlist）的受信任伺服器，發起有逾時邊界的傳統相容性探測。
- 只有在校驗到傳統版本回傳了合法的 `initialize` 正向結果後，才正式確認切換至傳統相容時代。
- 安全合併多個伺服器的確定性工具清單，杜絕名稱碰撞引發的無聲覆蓋災難。
- 在不憑空發明任何協定連線階段的前提下，將工具呼叫精確路由至其所屬的底層伺服器。

## The Problem｜問題

一個真實的 Agent 宿主環境通常需要同時與多個 MCP 伺服器保持通訊。它必須負責探測各伺服器的能力、合併多方工具目錄、解決重名衝突、精準路由轉發請求，並在實體傳輸中斷時優雅恢復。

`2026-07-28` 規範讓系統的穩定運行狀態大幅簡化，因為每一個請求皆為自包含的獨立個體。然而，啟動階段的向下相容性決策卻變得極為微妙。用戶端在啟動時可能遭遇：

- 完美支援使用者偏好版本的現代伺服器；
- 回傳了標準版本或標頭錯誤碼的現代伺服器；
- 從未聽聞過 `server/discover` 介面的傳統舊伺服器；
- 在接收到 `initialize` 之前保持靜默無聲的傳統伺服器。

將所有探測錯誤一概歸咎為「遇到了舊伺服器」是極其危險的反模式。一個格式畸形的現代請求、一個負載超載的伺服器、一個意外崩潰退出的行程、以及一個真實的舊版伺服器，皆可能表現出完全相同的連線逾時或連線關閉。這些訊號本質上充滿了語義歧義。用戶端必須將明確的維運者授權意圖，與真實的協定正向證據緊密結合，方可切換至傳統相容時代。

## The Concept｜核心概念

### 對等端點（Peer）而非協定連線階段

用戶端為每個伺服器行程或遠端端點維護一條本機對等端點記錄（Peer Record）：

- 實體傳輸層控制 handle 或發送函式參照；
- 選定的協定時代與具體版本；
- 最近一次探測發現的伺服器能力清單；
- 最近一次取得的確定性工具清單；
- 正在等待回傳的請求 ID 關聯表；
- 實體傳輸層健康監控狀態。

請注意：這純屬用戶端自身的本機簿記機制，絕非協定層級的連線工作階段狀態。在現代 MCP 規範下，伺服器在接收每一次請求時，依然各自獨立讀取當前的版本與能力宣告。

### 從零組裝每一個現代請求

```python
def modern_request(request_id, method, params, version, capabilities):
    return {
        "jsonrpc": "2.0",
        "id": request_id,
        "method": method,
        "params": {
            **params,
            "_meta": {
                "io.modelcontextprotocol/protocolVersion": version,
                "io.modelcontextprotocol/clientCapabilities": capabilities,
                "io.modelcontextprotocol/clientInfo": CLIENT_INFO,
            },
        },
    }
```

切勿僅在剛連線時於連線物件上掛載一次後設資料，便天真地假定後續所有通訊皆已自動攜帶。必須針對最終序列化送出的每一筆請求，進行顯式的壓印與檢查。

### 現代服務發現機制

`server/discover` 回傳伺服器支援的版本清單、能力宣告、操作說明、快取策略建議，以及推薦的伺服器識別資訊。用戶端據此挑選雙方共同相容的最高版本。

對於純現代用戶端而言，服務發現純屬選用操作；但在 stdio 傳輸層上強烈建議執行。因為某些傳統舊伺服器在初始化前也能偶發接受某些常規操作，若貿然直接發送 `tools/list`，可能會收到含糊的成功回應。`server/discover` 能夠為協定劃分出涇渭分明的時代分界線。

### stdio 相容性探測協定

一個具備雙版本相容能力的 stdio 用戶端，在發送任何其他業務請求前，會先發送攜帶偏好現代後設資料的 `server/discover`。結果必然落在以下三大類別之一：

1. **收到合法的 DiscoverResult**：證明伺服器為現代規範。選取雙方支援的版本，後續所有請求皆攜帶逐請求後設資料。
2. **收到已知的現代協定錯誤碼**：證明伺服器同樣理解現代協定。若收到 `-32022`，從其回傳的 `data.supported` 中挑選相容版本並以新請求 ID 重試；若為標頭或能力錯誤，修正請求內容。**絕不要**發送 `initialize`。
3. **模糊歧義訊號**：未知的 JSON-RPC 錯誤、連線逾時、連線異常中斷、或收到空白回應。這些訊號無法證明伺服器時代。除非該對等端點被顯式配置為允許傳統相容，否則必須一律採取安全預設（Fail Closed）直接報錯。

已知的現代協定標準錯誤代號：

- `-32020` HeaderMismatch（標頭與內文不符）
- `-32021` MissingRequiredClientCapability（缺少必備用戶端能力）
- `-32022` UnsupportedProtocolVersion（不支援的協定版本）

已知的現代錯誤意味著伺服器已確鑿無誤地證明了自己理解現代語義，此時即使該伺服器位於白名單中，發送 `initialize` 亦屬於非法的倒退降級。

絕不要將 `-32601`（MethodNotFound）視為確鑿的傳統版本證據。它至多只能讓一個預先列入白名單的端點，獲得一次嘗試發起傳統探測的資格。此規則同樣嚴格適用於逾時、連線關閉或空白回應。

### 白名單是維運者意圖，而非協定證據

向下相容性必須是針對特定鎖定端點的顯式配置：

```python
client.add_server("archive", archive_transport, allow_legacy=True)
```

將該授權嚴格綁定至具體的指令碼或端點 URL。嚴禁使用通配符（Wildcard）讓任意未知的伺服器自主將自身降級為寬鬆語義。未標註 `allow_legacy=True` 的端點在遇到模糊探測訊號時立刻宣告失敗，永遠不會收到 `initialize`。

允許清單僅代表賦予探測資格，並不代表時代已被選定。用戶端在傳輸層強制的硬性逾時邊界下發送一次 `initialize`，隨後必須嚴格驗證全數滿足以下條件：

- 回傳的 JSON-RPC 版本嚴格為 `2.0` 且請求 ID 吻合；
- 僅包含唯一的 `result`，且不含 `error`；
- 其 `protocolVersion` 嚴格落在用戶端配置的相容舊版本集合中；
- 包含物件型別的 `capabilities` 欄位；
- 包含非空字串 `name` 與 `version` 的 `serverInfo` 物件。

任何逾時、連線關閉、錯誤回應、格式畸形、ID 錯位或不支援的舊版本，皆必須立刻安全中斷。唯有在結構完全合法且版本相容的正向回應下，方可正式確立傳統時代。傳輸轉接層必須嚴格執行 `legacy_probe_timeout_ms` 逾時限制，而非僅僅記錄在日誌中。

確立的協定時代必須在該對等端點的生命週期內妥善快取，絕不要在每次呼叫前重複進行探測。

### 傳統相容模式是受約束的例外路徑

一旦受限探測確認回傳了合法的傳統正向證據，用戶端必須嚴格依照該舊版規格運作：

1. 校驗回應信封與關聯 ID。
2. 確認協商出的舊版本落在配置的合法相容集合內。
3. 記錄通過校驗的能力宣告與伺服器識別資訊。
4. 只有在全數檢查通過後，方可發送 `notifications/initialized`。
5. 在該實體傳輸生命週期內，全面採用舊版請求封裝格式。

這條路徑的存在僅是為了與已知的既有舊服務實現互通。它絕非新伺服器或新請求的標準設計。一旦底層傳輸重啟或連線端點變更，必須立刻拋棄時代快取並重新展開完整協商。

### 探測與快取工具清單

針對每個活躍的對等端點，呼叫 `tools/list`。現代回應中包含 `resultType`、`ttlMs` 與 `cacheScope`。在正確的授權邊界內恪守新鮮度建議；在快取過期或收到已訂閱的清單變更事件後主動重新整理。

用戶端在處理來自傳統舊伺服器的回應時，若缺少 `resultType`，必須寬容地將其視為 `"complete"`。絕不要對歷史舊版本強行索求現代快取欄位。

伺服器應當保證回傳項目的確定性排序。用戶端在合併前亦應在本地再次排序，確保本地工具註冊表順序不依賴行程啟動的隨機先後。

### 防碰撞的命名空間合併策略

當兩個獨立的伺服器皆對外公開了名為 `search` 的工具時，必須執行預先宣告的衝突解決策略：

1. **衝突時加前綴（Prefix on collision）**：保留首個註冊的標準名稱，將後續衝突項命名為 `<server>/<tool>`。
2. **衝突時拒絕加載（Reject on collision）**：直接拒絕載入重複工具，並在日誌中拋出清晰的組態錯誤。
3. **無聲覆蓋（Silent overwrite）**：**嚴格禁用**。這會掩蓋模型選取的動作究竟被發送給哪一台實體伺服器的真相。

用戶端在內部同時儲存標準名稱與本機名稱。模型看見的是對外暴露的標準名稱；而向目標伺服器發送的 `tools/call` 則使用該伺服器當初自行宣告的本機名稱。

### 請求路由轉發機制

路由轉發本質上是純粹的確定性查表映射：

```text
canonical tool name
  -> peer name + local tool name
  -> new JSON-RPC request id
  -> modern request metadata or explicit legacy shape
  -> matching response id
```

當目標伺服器的底層傳輸處於不可用狀態時，絕不要盲目轉發呼叫。應當先重新建立連線或重啟行程，重新完成服務發現與 `tools/list` 探測。若某個正在傳輸中的現代請求因連線中斷而遺失，在該動作的安全策略明確允許的前提下，可使用全新的 JSON-RPC 請求 ID 重新發起安全重試。

### 通知與訂閱機制

現代清單與資源變更事件，僅能在用戶端主動開啟的 `subscriptions/listen` 串流上推送。用戶端發送過濾條件，等待收到 `notifications/subscriptions/acknowledged` 確認通知，並透過後設資料中的監聽請求 ID 與事件進行精確關聯。

一旦連線斷開，應當建立全新的監聽請求，並主動重新拉取受影響的相關清單或資源。現代事件串流不支援透過 `Last-Event-ID` 進行斷點續傳。

### 嚴禁伺服器主動發起逆向請求

現代伺服器絕不允許自發發起獨立的 JSON-RPC 請求來要求大模型取樣、進行人機問答引導或存取本機目錄。它們會回傳 `input_required`，由用戶端在本地滿足對應的輸入請求後，使用全新的請求 ID 重新發起最初的呼叫。

在處理輸入請求期間，切勿卡死對等端點的回應讀取線程。妥善維護關聯 ID，並為重試操作派發全新的 JSON-RPC 請求識別碼。

## Use It｜實際應用

`code/main.py` 利用行程內部的虛擬對等端點函式進行模擬，使所有協定層面的決策邏輯一覽無遺。它同時連接兩個現代端點與一個被顯式列入允許清單的傳統端點，隨後執行工具清單的合併與動態路由轉發。傳輸回呼接收了嚴格的逾時預算，杜絕相容路徑發生無約束的懸掛探測。

```bash
cd code
python3 main.py
python3 -m unittest discover tests -v
```

自動化測試精確驗證了一般常規展示極易遺漏的關鍵邊界：

- 現代請求在每一次調用時皆重複攜帶後設資料；
- 收到 `-32022` 錯誤時，以現代方式協商重試，絕不錯誤觸發初始化；
- 已知的現代協定錯誤碼永遠不會引發版本降級，即便該伺服器具備白名單授權；
- 連線逾時、連線中斷、空白回應與未知錯誤在未經白名單授權時，絕不擅自觸發 `initialize`；
- 白名單端點唯有在收到合法且支援的 `initialize` 正向結果後，才被允許確立為傳統時代；
- 畸形或不支援的舊版回應會讓端點維持在不可用狀態；
- 成功選定的協定時代會在該實體傳輸生命週期內被妥善快取。

## Exercises｜練習

1. 構造一個虛擬伺服器使其回傳 `-32022` 且雙方無任何共同支援的版本。驗證用戶端是否會果斷報錯終止，而非盲目發送 `initialize`。
2. 將一個虛擬舊版伺服器列入白名單，但故意讓其受限的 `initialize` 探測發生逾時。證明該端點會始終保持在 `unknown` 與不可用狀態。
3. 針對兩個相異的授權邊界分別建構宣告為 `cacheScope: "private"` 的工具清單。驗證用戶端絕不會將某一個邊界內快取的私有結果挪用至另一個邊界中。
4. 將命名空間碰撞解決策略修改為「直接拒絕（Reject）」，並使程式在啟動時拋出同時指名兩台衝突伺服器名稱的明確錯誤。
5. 實作一個有限狀態的 `subscriptions/listen` 模擬器。當事件串流中斷時，使用全新的請求 ID 重新發起監聽，並主動重新整理相應的工具註冊表。

## Key Terms｜關鍵術語

| 術語 | 實際意義 |
|------|---------|
| Peer | 對等端點；用戶端針對單一實體伺服器傳輸連線及其探測資料維護的本機記錄 |
| Protocol era | 協定時代；劃分為「現代單請求自包含後設資料」與「傳統連線級初始化語義」 |
| Discovery probe | 服務發現探測；在 stdio 上發起的首個 `server/discover` 請求，用以判定協定時代 |
| Recognized modern error | 已知的現代協定錯誤代號；確鑿證明伺服器具備現代語義，嚴禁執行傳統降級 |
| Legacy allowlist | 傳統相容允許清單；維運者針對特定鎖定端點顯式開放單次相容性探測的配置 |
| Positive legacy evidence | 傳統正向證據；針對受支援舊版本所收到的合法、ID 吻合的 `initialize` 成功回應 |
| Merged namespace | 合併命名空間；跨越所有活躍伺服器端點所對外暴露的標準工具名稱集合 |
| Collision policy | 衝突解決策略；面對不同伺服器宣告重名工具時採取的「加前綴」或「拒絕加載」規範 |
| Era cache | 時代快取；為單一實體傳輸端點持久暫存的現代或傳統協定運作模式 |
| Transport recovery | 傳輸恢復機制；重新建立連線、重新探測服務、重新拉取清單，並使用新 ID 重試 |
