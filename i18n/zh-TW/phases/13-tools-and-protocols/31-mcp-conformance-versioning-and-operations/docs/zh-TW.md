# MCP 符合性工程學：版本控制、證據鏈與維運治理

> 一台伺服器絕非單純因為最理想路徑在某個 SDK 下恰好跑通，便代表其具備標準符合性。真正的符合性活在實體傳輸線路上、活在跨版本邊界處、活在反向代理等中繼節點之間，以及遭遇系統回滾時的嚴苛考驗中。

**Type:** Build
**Languages:** Python
**Prerequisites:** Phase 13 · 09 (transports), Phase 13 · 17 (gateways), Phase 13 · 30 (registry admission)
**Time:** ~100 minutes

## Learning Objectives｜學習目標

- 將 MCP 規範性技術標準轉化為確定性的黃金標準傳輸日誌（Golden Transcripts）與負向反例測試日誌（Negative Transcripts）。
- 將嚴格的 `2026-07-28` 現代行為與受配額約束的舊版向下相容回退邏輯清晰劃分。
- 嚴格區分「具備前向相容性的未知附加欄位」與「非法未知的 `resultType` 判別式」。
- 客觀比對原始 JSON-RPC 傳輸線路證據與經 SDK 封裝正規化後的檢視差異。
- 透過真實的代理伺服器邊界，驗證 HTTP 標頭與主體資料的絕對一致性。
- 結合經脫敏抹除的傳輸日誌、健康度指標與回滾證據，建構自動化發布檢核門檻（Release Gate）。

## The Problem｜問題

你的用戶端透過官方 SDK 成功調用了 `tools/list`，順利取得了工具清單，整合測試亦綠燈通過。

然而，該表面結果卻遺留了諸多攸關系統生死的致命疑問：

- 該請求是否真的攜帶了現代標準的逐請求協定後設資料？
- `MCP-Protocol-Version`、`Mcp-Method` 與 `Mcp-Name` 標頭是否與 JSON-RPC 請求主體逐字一致？
- 實體線路上的回應是否真包含合法的 `resultType`，抑或是 SDK 在底層自動捏造補齊的？
- 當未來的全新附加欄位抵達時，用戶端是會優雅保留還是盲目丟棄？
- 當伺服器回傳已識別的現代標準錯誤碼時，用戶端是否會錯誤觸發舊版初始化握手？
- 中繼代理伺服器是否原汁原味地保留了源站的 HTTP 狀態碼與 JSON-RPC 錯誤結構？
- 通知序列化模組是否意外向外發送了嚴格禁止的 JSON-RPC 回應？
- 維運團隊能否在不洩漏任何機密的前提下，確鑿證明版本晉級或緊急回滾的客觀依據？

符合性（Conformance）是一組可被實體觀測的系統不變量集合。在正式環境真實流量暴露這些盲區之前，我們必須親手打造一套能完整捕獲這些不變量的測試控端。

```figure
mcp-conformance-operations
```

## Start With Version Eras｜始於版本時期的清晰劃分

MCP `2026-07-28` 修訂版採用完全自包含的逐請求後設資料。現代標準請求必須攜帶 `params._meta.io.modelcontextprotocol/protocolVersion` 與 `params._meta.io.modelcontextprotocol/clientCapabilities`。精確的命名空間鍵名至關重要；裸露的 `protocolVersion` 或 `clientCapabilities` 別名全屬格式損壞。當 HTTP 邊界存在同步對映的路由標頭時，其數值必須與 JSON-RPC 主體完全吻合。現代成功的結果必須顯式包含 `resultType`。

而截至 `2025-11-25` 的舊版本則採用早期的初始化握手架構。缺少 `resultType` 的舊版結果，唯有在用戶端已顯式選定該舊版時期後，方獲准被解讀為 complete。

切勿設計同時相容兩種結構的寬鬆校驗器。必須嚴格分立兩大路徑：

| 處理路徑 | 進入資格的客觀證據 | 缺少 `resultType` 的處置 | 初始化握手行為 |
|---|---|---|---|
| 現代標準路徑（Modern） | 成功的 `server/discover` 或已識別的現代標準回應 | 判定為非法無效 | 絕非預設路徑 |
| 舊版相容路徑（Legacy） | 位於配置白名單中，且在現代探測無果後收到合法的舊版 `initialize` 結果 | 解讀為 complete | 該時期強制必備 |

此種防禦性分離，能徹底防止實作損壞的現代節點因寬鬆校驗而僥倖過關。

### 嚴格模式（Strict mode）

嚴格模式強制要求現代行為的客觀證明。一次成功的 `server/discover` 即可確立現代路徑；一個已識別的現代 JSON-RPC 錯誤碼亦能證明該節點屬於現代架構。此時應當修正請求參數或終止通訊。**絕不可**因為伺服器回傳了 `-32020`、`-32021` 或 `-32022` 錯誤碼而擅自降級至舊版模式！

### 降級相容模式（Fallback mode）

降級模式首先執行單次受限的現代探測。遇到連線逾時、空回應、連線中斷或無法辨識的回應皆屬於「非結論性狀態（Inconclusive）」，這完全無法證明對端必然屬於舊版架構。唯有在目標端點預先經過白名單顯式授權向下相容時，方允許發送單次受限的舊版探測；且用戶端唯有在驗證該探測的 `initialize` 結果與協商出的舊版修訂版本後，方可切換至舊版路徑。

降級絕非「遇到任何報錯就盲目嘗試舊版」。已識別的現代錯誤包含具體的修正指引；盲目降級只會掩蓋標頭不符、缺失能力宣告或版本不支援等底層真實問題。

這能徹底防止中間人反向代理或網路中斷透過故意丟棄現代回應來發動降級攻擊。將端點策略、非結論性的現代觀測、確鑿的舊版正向證據以及選定的時期共同記錄於審計日誌中。

在每份傳輸日誌旁明確標註選定的時期。若缺少該事實，同一個欄位的缺漏在某次測試中看似合法，在另一次測試中卻被判定為非法。

## Build a Transcript Corpus｜建置全鏈路傳輸日誌語料庫

一份傳輸日誌測試資料（Transcript Fixture）忠實記錄跨越實體邊界的真實內容，而非單純記錄 SDK 呼叫結果：

```json
{
  "name": "golden-modern-list",
  "era": "modern",
  "headers": {
    "MCP-Protocol-Version": "2026-07-28",
    "Mcp-Method": "tools/list"
  },
  "request": {
    "jsonrpc": "2.0",
    "id": 1,
    "method": "tools/list",
    "params": {
      "_meta": {
        "io.modelcontextprotocol/protocolVersion": "2026-07-28",
        "io.modelcontextprotocol/clientCapabilities": {}
      }
    }
  },
  "responseStatus": 200,
  "responseBody": {
    "jsonrpc": "2.0",
    "id": 1,
    "result": {
      "resultType": "complete",
      "tools": []
    }
  }
}
```

維護兩大核心測試資料類別。

### 黃金標準傳輸日誌（Golden Transcripts）

黃金日誌負責證明獲准接受的標準合規行為：

- 現代服務發現或方法請求，伴隨吻合的後設資料與 HTTP 標頭；
- 包含必備欄位的 `complete` 成功結果；
- 當方法支援追加輸入時回傳的 `input_required` 結果；
- 僅在預先宣告對應能力後方允許回傳的擴充功能結果；
- 缺少 `resultType` 但嚴格位於已選定舊版時期的相容結果；
- 正確處理通知且不向外輸出任何 JSON-RPC 回應。

黃金日誌應當力求精確而非臃腫。保持易變的 ID 與時間戳記具備確定性，或在比對前實施正規化。

### 負向反例測試日誌（Negative Transcripts）

負向日誌負責證明系統具備嚴密的拒絕攔截能力：

- 標頭數值與請求主體不符；
- 缺失逐請求的必備能力宣告；
- 支援的版本比對不相容；
- 現代結果缺失必備的 `resultType`；
- 未知或未預先宣告的未知 `resultType`；
- 回應的 `jsonrpc` 欄位非 `2.0`，或 ID 數值／JSON 型別不符；
- 回應同時包含 `result` 與 `error`，或兩者皆缺漏；
- 錯誤物件缺少整數 `code` 或字串 `message`；
- 已知協定錯誤被映射至錯誤的 HTTP 狀態碼；
- 針對單向通知意外回傳了 JSON-RPC 回應；
- JSON-RPC 信封結構畸形；
- 中繼代理伺服器吞沒了底層協定錯誤。

針對每個負向案例，必須明確斷言被攔截的具體邊界與穩定的錯誤代號。「呼叫失敗」是極度軟弱的斷言；代理端捏造的 HTTP 500 與源站回傳的 `-32020` 雖然皆表現為失敗，但向維運人員傳遞的資訊卻天差地遠。

標頭不一致測試資料必須包含伺服器真實回傳的 HTTP 400 JSON-RPC 回應，並帶有匹配的請求 ID 與錯誤碼 `-32020`。每當本地校驗器檢測到 `HeaderMismatch` 時，必須強制自動比對該回應；切勿將回應校驗設計為可選旗標。若測試控端在自身請求校驗器拋出例外後便提早中止，它測試的僅僅是自己的程式碼，而非伺服器在實體線路上的真實行為。

官方 MCP 符合性測試專案是極佳的外部參考基準。同時務必維護專屬的本機傳輸日誌，因為它們精準記錄了你的專屬代理、SDK、身分驗證、自訂擴充與發布途徑，這是通用套件無法預知的。

## Header Values Must Match the RPC Body｜標頭數值必須與 RPC 主體逐字相符

在現代 Streamable HTTP 模式下，中繼節點可利用同步對映的標頭進行分流或策略審查。然而，JSON-RPC 主體始終是該協定的最高權威來源。兩者不一致屬於嚴重的資料完整性破壞，而非在兩者間隨意二選一的提示信號。

請嚴格遵循以下順序執行校驗：

1. 剖析並校驗 JSON-RPC 信封格式與後設資料型別。
2. 比對 `MCP-Protocol-Version` 標頭與 `params._meta.io.modelcontextprotocol/protocolVersion`。
3. 比對 `Mcp-Method` 標頭與 `method` 欄位。
4. 當該方法包含路由名稱時，比對 `Mcp-Name` 標頭與主體中的對應數值。
5. 唯有在上述完全一致性確立後，方可進一步裁決版本與能力是否受系統支援。

此執行順序能清晰區分「標頭不一致（`-32020`）」與「版本不支援（`-32022`）」。它亦能徹底防範代理網關依標頭名稱放行授權、而後端源站卻實質執行了完全不同的主體方法的安全漏洞。

HTTP 欄位名稱不分大小寫，但其參數數值嚴格區分大小寫。在檢索前先將標頭名稱正規化，並拒絕衝突的重複標頭。針對不安全、非 ASCII 或帶有前後空格的 `Mcp-Name`，必須在與主體比對前，將標準的 `=?base64?{Base64EncodedValue}?=` UTF-8 哨兵格式精確解碼。若哨兵格式不完整、Base64 非法、UTF-8 解碼失敗或直接以未編碼的不安全明文傳輸，一律回傳 `-32020`。帶有未編碼前後空格的標頭屬於非法無效，即便主體中包含完全相同的字元亦不例外，因為該字串在傳輸前依法必須強制進行 Base64 編碼。

中繼節點可能在請求抵達 MCP 伺服器前便因 HTTP 畸形而直接拒絕，此時其失敗可能僅表現為純 HTTP 錯誤而無 JSON-RPC 信封。清楚記錄該拒絕究竟來自中繼節點還是源站。源站 MCP 伺服器在處理合法的 JSON-RPC 請求時，必須嚴格遵循協定錯誤契約。

## Unknown Fields Are Not Unknown Results｜未知附加欄位絕非未知的執行結果

前向相容性（Forward Compatibility）需要兩條涇渭分明的處理規則。

### 具備前向相容性的未知附加欄位（Additive unknown fields）

結果物件與 `_meta` 字典在未來可能會擴充全新欄位。校驗器應依據自身在架構中的定位，選擇保留或忽略這些新增欄位，除非該欄位違反了保留關鍵字契約。範例實作在證據中完整保留了原始結果，並接受位於已知結果旁的 `futureHint` 欄位。

若你扮演的是透明代理，保留未知欄位通常比盲目剃除更加安全；若你扮演的是終端應用程式，忽略未知欄位是完全合理的。差異比對測試應當清晰指出 SDK 是否丟棄了該欄位，確保該行為屬於經過深思熟慮的架構抉擇。

### 未知的 `resultType` 判別式

`resultType` 是一個關鍵的狀態辨識器（Discriminator）。核心現代結果僅允許 `complete` 或 `input_required`。擴充功能唯有在預先宣告對應能力的前提下，方允許引入全新數值（例如在協商出 Tasks 能力後允許出現 `task`）。

未知或未經宣告的辨識器**絕不可**被盲目當作 complete 放行！用戶端根本無從得知自己因此擅自拋棄了何等關鍵的非同步生命週期。必須堅決予以拒絕！

同一個原始回應可能同時包含「可接受的未知屬性」與「完全不可接受的未知結果型別」。必須對這兩種情境分別撰寫測試案例。

辨識器只是最外層檢核。通過辨識器後，必須進一步嚴格校驗特定方法的酬載結構。合法的 `tools/list` 結果必須包含 `tools` 陣列，且其描述元具備非空的唯一名稱、有意義的描述與物件根節點 `inputSchema`。`task` 結果嚴格僅適用於具備 Tasks 能力的 `tools/call`，且必須包含 `taskId`、已知狀態、建立與更新時間戳記、`ttlMs` 以及合法的選用輪詢間隔。`completion/complete` 結果必須包含 `completion` 物件，且建議字串不超過 100 筆、選填的非負整數 `total` 不小於回傳筆數，並附帶選填的布林值 `hasMore`。拼寫正確的 `resultType` 絕無法讓結構畸形的酬載蒙混過關。

## The Notification Invariant｜單向通知的不變量契約

JSON-RPC 通知嚴格不帶 `id` 欄位。接收端**絕不可**對外發送任何 JSON-RPC 成功或錯誤回應。

針對已獲接收的 HTTP 通知結構，測試控端預期接收 HTTP `202` 狀態碼且主體為空。MCP `2026-07-28` 在 Streamable HTTP 上未定義任何核心的用戶端至伺服器單向通知。範例程式碼僅採用帶有命名空間的課程擴充通知來測試單向序列化不變量，切勿將其誤傳為全新的核心協定方法。

測試必須直接覆蓋底層序列化模組，而非僅僅測試業務處理函式。處理常式可能回傳了 `None`，但外層中介軟體卻自作主張將其包裝為 JSON 成功物件。必須直接捕獲最終發送至實體線路上的位元組。

## Add an SDK Differential｜導入 SDK 抽象層差異對比

各大 SDK 通常會將實體線路物件封裝為便捷的高階程式語言型別。這固然提升了開發體驗，但經過高階封裝的物件無法證明線路上實際接收到了什麼。

針對每個高風險測試案例，記錄以下四種檢視：

1. 未經 SDK 解碼前的原始 HTTP 狀態碼、標頭與回應主體；
2. SDK 正規化後的物件回傳值或拋出的例外；
3. 針對選定時期的預期語意投影；
4. 被 SDK 提取、捏造、剃除或篡改的具體欄位。

範例程式碼允許 SDK 在比對業務酬載時，合理移除 `resultType`、`_meta`、`ttlMs` 與 `cacheScope` 等底層線路簿記欄位；但它會嚴肅回報遺失的 `futureHint`，因為這項未知的語意欄位被 SDK 無端抹除了。

切勿假設每處差異皆屬於 SDK 缺陷。此機制的重點在於讓所有資料轉換過程無所遁形。依據系統定位決定是作為應用端忽略附加欄位，還是作為透明中繼代理完整保留它。

針對你所發布的每款 SDK 及其版本執行差異對比。若兩款 SDK 對完全相同的傳輸日誌解讀出不同的結構，發布策略應當明確指明何者合規，而非事後隨意挑選最討喜的輸出。

## Capture Proxy Evidence｜完整捕獲反向代理客觀證據

正式環境中最常見的 MCP 故障皆跨越多個獨立行程。必須記錄三種全域檢視：

| 觀測檢視 | 最低必備客觀證據 |
|---|---|
| 入站（Ingress） | 請求標頭、JSON-RPC 主體、Content-Type、鑑權路由、接收時間戳記 |
| 源站（Origin） | 轉發後的標頭與主體雜湊、源站 HTTP 狀態、回應標頭與主體 |
| 出站（Egress） | 用戶端可見的狀態碼、標頭、主體與發送時間戳記 |

範例程式碼能精準偵測兩種常見的中繼破壞：

- 源站回傳的 HTTP 400 或 404 JSON-RPC 錯誤被反向代理粗暴壓制為全域通用的 HTTP 500；
- 最終出站的 JSON-RPC 主體與源站發出的原始主體不符。

進一步加入針對 Content-Type、`Accept`、壓縮編碼、請求專屬 SSE、快取標頭與 Trace 關聯的部署斷言。在合規允許下捕獲 TLS 終結點兩側的真實狀況。絕不可僅為了證明連線通暢而將機密金鑰寫入日誌。

## Redact Before Evidence Leaves Memory｜證據離開記憶體前實施強制抹除

資料抹除（Redaction）屬於符合性工程的原生環節，絕非事後補救工作。在資料進行序列化、雜湊計算、寫入日誌、儲存測試產物或上傳故障包之前，必須強制完成抹除。

範例程式碼在比對鍵名時先進行大小寫折疊並移除所有分隔符號，隨後遞迴抹除匹配 `Authorization`、`Cookie`、`Set-Cookie`、`X-Api-Key`、`accessToken`、`clientSecret`、`registrationAccessToken`、`token`、`password`、`secret` 與 `api_key` 的欄位數值。標準化規則與黑名單必須採用完全相同的形式，確保駝峰命名（camelCase）、連字號、底線與小數點等命名風格變體完全無法互相繞過防禦。生產收集器應進一步針對具體方法加入參數審查策略，因為如 `query` 般看似無害的欄位內部依然可能包含個人隱私資料。

對抹除後的證據包進行密碼學雜湊計算。僅在面臨特定資安調查時，方允許在受限的短期系統中留存原始封包。雜湊值確鑿證明了是哪份經抹除的證據主導了系統決策，同時絕不洩漏被剔除的敏感數值。

## Make Health and Rollback Part of the Gate｜將健康度指標與回滾能力納入發布門檻

協定層面的符合性是發布的必要條件，但絕非充分條件。一個完全符合協定規範的候選版本，依然可能發生連線逾時、記憶體洩漏或拖垮下游依賴。

在逐步放量前預先定義健康評估時間視窗：

- 最小取樣請求筆數；
- 允許的最大錯誤率上限；
- 允許的最大延遲百分位數（P95/P99）；
- 飽和度或系統資源配額上限；
- 實體觀測持續時間；
- 與已准入 Baseline 基準線的對照分析。

在放量前同樣必須預先確立回滾證據：

- 精確的先前版本號；
- 准入審查證據雜湊；
- SHA-256 產物與描述元鎖定基準；
- 當前註冊表即時狀態；
- 當前即時健康檢查結果；
- 流量路由復原標準作業程序；
- 由受信任之發布控制器身分對上述欄位簽發的合法認證憑證。

要求該回滾目標在版本晉級**之前**便已通過驗證且處於完全健康狀態，而非在候選版本崩潰後才手忙腳亂去驗證。一個缺乏可用復原退路的發布版本，根本不具備生產就緒度。

若候選版本發生故障而回滾目標缺乏上述證據，應當果斷阻斷流量而非盲目猜測。「隨意切換回原本運行的程式」絕非合格的工程維運控制。

切勿將系統就緒度簡化為非空字串、`healthy: "yes"` 或任意模糊證詞。範例程式碼嚴格要求精確型別、active 狀態、三組 SHA-256 雜湊、受信簽名者以及覆蓋完整回滾酬載的有效 HMAC-SHA-256 認證憑證。教學中的確定性金鑰僅屬展示測試資料；在正式環境中，必須在發布邊界注入受保護的密鑰、KMS 驗證服務或公鑰認證驗證器。

發布門檻亦堅決拒絕空的傳輸日誌、空的 SDK 差異檢視或空的代理證據。每個來源皆必須攜帶合法的證據雜湊。全綠的健康度指標絕無法填補一道從未被實際觀測過的系統邊界。

## Build It｜動手實作

運行純 Python 標準函式庫實作的符合性測試控端：

```bash
cd phases/13-tools-and-protocols/31-mcp-conformance-versioning-and-operations
python3 code/main.py
```

演示程式會精確執行全部 15 套黃金標準與負向反例傳輸日誌（包含合法與畸形的補全結果）、客觀比對原始線路結果與 SDK 視角、深入審查一個將源站錯誤粗暴壓制為 HTTP 500 的代理伺服器、評估健康度指標、驗證回滾證據的密碼學真實性，並最終挑選該回滾目標。

預期輸出結構：

```json
{
  "transcriptsPassed": 15,
  "transcriptsTotal": 15,
  "sdkDroppedFields": ["futureHint"],
  "proxyIssues": [
    "proxy collapsed a protocol error into HTTP 500",
    "proxy changed the origin JSON-RPC body"
  ],
  "releaseAction": "rollback",
  "evidenceDigest": "..."
}
```

請依以下順序研讀 `code/main.py` 實作：

1. `validate_request()`：強制執行感知時期的請求與標頭校驗規則；
2. `validate_result()`：清晰劃分缺失的舊版判別式、合法的現代數值、擴充功能與未知非法結果；
3. `select_era()`：實作嚴格模式與受限相容模式的決策引擎；
4. `run_transcript()`：端到端執行黃金與負向測試案例；
5. `compare_sdk_view()`：無所遁形地暴露 SDK 的封裝轉換差異；
6. `inspect_proxy()`：深入交叉比對入站、源站與出站三方證據；
7. `redact()`：在雜湊計算前遞迴抹除機密資訊；
8. `rollback_evidence_ready()`：校驗精確的鎖定欄位與受信發布認證憑證；
9. `ReleaseGate.evaluate()`：綜合判定符合性、SDK、代理、健康度與回滾全套證據。

## Use It｜實際應用

在以下四大關鍵節點執行該測試控端：

1. 每次底層實作變更時，透過行程內測試配接器執行；
2. 針對建置出的真實用戶端與伺服器二進位程式，跨越實體傳輸層執行；
3. 在預備環境（Staging）中，穿透實體部署的反向代理與閘道器執行；
4. 在金絲雀（Canary）灰度發布期間，結合即時健康度與回滾證據持續執行。

跨各層級始終維持相同的穩定測試案例名稱。`negative-header-body-mismatch` 在單元測試、端到端測試、代理測試與金絲雀報告中皆應代表完全相同的系統不變量。證據雜湊會因為觀測邊界的不同而改變；但工程需求本身絕不改變。

將測試案例 Schema 納入版本控制系統。將脫敏抹除後的執行證據存入發布管理系統中。原始未經脫敏的封包日誌嚴格僅能在遭遇緊急事故時、於受限存取途徑內短期留存。

## Interactive Lab｜互動實驗

### 實驗 A：驗證版本時期的邊界隔離

在 `code` 目錄下開啟 Python 互動式環境：

```bash
cd phases/13-tools-and-protocols/31-mcp-conformance-versioning-and-operations/code
python3 -q
```

隨後執行：

```python
from main import *
validate_result({"tools": []}, "legacy")
validate_result({"tools": []}, "modern")
```

舊版呼叫會自動推導出 complete；而現代呼叫則直接拋出 `ProtocolViolation`。現在測試相容降級機制：

```python
select_era({"kind": "timeout"}, "fallback")
select_era(
    {"kind": "timeout"},
    "fallback",
    legacy_allowed=True,
    legacy_evidence={"kind": "initialize_success", "protocolVersion": LEGACY_VERSION},
)
select_era({"kind": "jsonrpc_error", "code": -32021}, "fallback")
```

第一次逾時會安全中斷（Fail-closed），因為單純的靜默絕非舊版證據。第二次呼叫成功選定舊版，因為策略顯式允許且捕獲到了合法的舊版初始化結果。而第三次遭遇已識別的缺失能力錯誤時，系統精準鎖定於現代路徑。

### 實驗 B：未知附加欄位 vs 未知判別式

```python
validate_result({"resultType": "complete", "tools": [], "futureHint": True}, "modern")
validate_result({"resultType": "future_mode", "tools": []}, "modern")
```

第一個結果順暢保留了 `futureHint`；第二個結果則被果斷拒絕，因為其生命週期判別式完全未知。

### 實驗 C：檢視 SDK 封裝轉換

```python
compare_sdk_view(
    {"resultType": "complete", "tools": [], "futureHint": {"mode": "new"}},
    {"tools": []},
)
```

依據系統定位決定你的元件是允許忽略 `futureHint` 還是必須向下游透傳它。將該決策明確寫入發布策略中，絕不可靜默忽視該差異。

### 實驗 D：修復反向代理

修改演示程式中的通訊紀錄，使出站資料原汁原味地保留源站的 HTTP 狀態碼與主體內容。再次執行 `python3 main.py`。代理問題將會消失，但 SDK 差異依然會阻止版本晉級。隨後在 SDK 檢視中補齊 `futureHint`，親眼見證在所有證據全數通過後，決策動作如何順利切換為 `promote`（晉級發布）。

## Practice Lab｜實戰實驗

為控端擴充請求專屬的 SSE 傳輸日誌評測支援。

具體需求：

- 捕獲 HTTP 回應狀態、Content-Type、有序的 SSE 事件串流以及連線終止信號；
- 證明每個 JSON-RPC 事件皆包含合法的時期專屬結果或錯誤物件；
- 新增負向案例：檢測並攔截在轉發前將整條串流完全緩衝扣押的反向代理；
- 新增負向案例：檢測並攔截 JSON-RPC ID 與原始請求不符的異常 SSE 事件；
- 在將證據持久化前，對事件資料實施深度脫敏抹除；
- 將串流持續時長、首事件延遲與事件總數納入健康度評估時間視窗中；
- 確保當串流異常時，發布門檻僅允許切換至具備客觀證據的回滾目標。

成功標準：完全相同的測試案例在直接連線與穿透代理時皆能順利執行，並產出能精準定位究竟是哪道邊界改變了系統行為的結構化報告。

## Verify It｜成果驗證

運行演示程式與確定性測試套件：

```bash
cd phases/13-tools-and-protocols/31-mcp-conformance-versioning-and-operations
python3 code/main.py

```

測試驗證必須確鑿證明：

- 現代標準請求強制要求精確的命名空間後設資料鍵名；
- HTTP 標頭名稱不分大小寫完成比對，且編碼後的 `Mcp-Name` 數值被精準還原；
- 標頭與主體不一致時，精準回傳現代不一致錯誤碼；
- 嚴格校驗回應協定版本、ID 數值與型別、結果／錯誤互斥性、錯誤結構與 HTTP 映射；
- 強制執行方法專屬的工具清單、長任務與自動補全酬載約束；
- 每個觀測到的 `HeaderMismatch` 皆伴隨真實的 HTTP 400 JSON-RPC `-32020` 回應；
- 原始未編碼的 `Mcp-Name` 空格被果斷拒絕，而經 Base64 哨兵編碼的空格能精準還原；
- 缺少 `resultType` 唯有在已選定的舊版時期中方獲准放行；
- 未知附加欄位能通過原始校驗，而未知的結果型別被堅決拒絕；
- 擴充功能結果型別嚴格要求預先宣告對應能力；
- 已識別的現代標準錯誤碼絕不觸發舊版相容降級；
- 單向通知絕不向外發送任何 JSON-RPC 回應；
- SDK 底層簿記清理與業務語義欄位遺失被清晰區分；
- 代理錯誤壓制被精準檢測，且機密憑證在駝峰命名與各式分隔符號下皆被遞迴抹除；
- 版本晉級強制要求非空的傳輸日誌、SDK 檢視、代理檢視與健康的維運證據；
- 版本晉級與安全回滾皆強制要求經過身分認證、已鎖定、活躍且健康的回滾目標。

## Production Failure Modes｜正式環境失效模式

| 失效情境 | 脆弱測試所回報的表象 | 測試控端必須證明的真相 |
|---|---|---|
| SDK 擅自捏造補齊缺失的判別式 | 「tools/list 測試通過」 | 原始現代結果缺少 `resultType`，實質上屬於非法無效 |
| 用戶端遭遇 `-32021` 後擅自降級 | 「舊版重試成功運作」 | 已識別的現代錯誤嚴格禁止觸發舊版降級回退 |
| 未知結果型別被盲目當作 complete | 「回應成功解析」 | 未經宣告的非同步生命週期判別式被堅決拒絕 |
| 代理核准 A 工具而源站執行 B 工具 | 「請求已順利抵達伺服器」 | `Mcp-Name` 在每一跳中皆嚴格等於主體路由名稱 |
| 控端在讀取伺服器回應前便拋出例外 | 「標頭不一致測試通過」 | 伺服器實質回傳的 HTTP 400 與 `-32020` 回應被捕獲並校驗 |
| 代理將源站 400 壓制為通用 500 | 「上游伺服器發生錯誤」 | 源站與出站的 HTTP 狀態碼及 JSON-RPC 主體被完整保留 |
| 通知中介軟體擅自輸出 `{result: null}` | 「處理常式回傳 None」 | 最終出站主體為空，且實體線路上不存在任何 JSON-RPC 回應 |
| SDK 擅自剃除未知的附加欄位 | 「強型別物件比對吻合」 | 原始檢視與正規化檢視清晰暴露被遺失的具體欄位 |
| 故障除錯產物意外洩漏 Bearer 權杖 | 「除錯封包已成功上傳」 | 抹除作業在雜湊計算、日誌記錄與檔案上傳前已強制完成 |
| 金鑰命名風格繞過了脫敏規則 | 「黑名單包含 api_key」 | 駝峰命名與各式分隔符號變體在正規化後共享統一黑名單 |
| 金絲雀發布缺乏足夠樣本卻顯示健康 | 「錯誤率為零」 | 強制設定並核驗最小取樣請求筆數下限 |
| 回滾機制選取了未知的未知建置版本 | 「已成功復原至先前部署」 | 目標版本、准入雜湊、實體鎖定基準、狀態與健康度全數在場 |

## Operational Rule｜維運準則

嚴格測試你所發送的每個位元組、中繼節點所轉發的每個位元組、各 SDK 所暴露的真實語義，以及維運團隊在高壓下所依賴的客觀證據。向下相容是一條顯式的架構路徑；安全回滾是一項由證據支撐的發布動作。兩者皆絕不應當成為寬鬆剖析器的偶然副作用。
