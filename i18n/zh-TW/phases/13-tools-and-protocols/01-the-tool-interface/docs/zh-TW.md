# 工具介面——為何 Agent 需要結構化 I/O（The Tool Interface — Why Agents Need Structured I/O）

> 語言模型生成 token；軟體程式執行具體動作。橫跨於兩者之間的鴻溝，正是「工具介面（Tool Interface）」：一份讓模型能夠請求動作、並由宿主（Host）代為執行的精確協定契約。2026 年的所有主流技術堆疊——包含 OpenAI、Anthropic 與 Gemini 的函式呼叫（Function Calling）、MCP 的 `tools/call`、以及 A2A 的任務部分——無一例外皆是同一套四步驟迴圈的不同具體編碼實踐。本課將為這套核心迴圈定名，並展示驅動它所需的最簡化工程機制。

**Type:** Learn
**Languages:** Python (stdlib, no LLM)
**Prerequisites:** Phase 11 (LLM completion APIs)
**Time:** ~45 minutes

## Learning Objectives｜學習目標

- 解釋為何僅能自回歸生成文字的 LLM，本質上無法憑藉自身直接對真實物理與數位世界發起操作。
- 繪製標準四步驟工具呼叫迴圈（宣告描述 → 決策發起 → 實體執行 → 觀察回饋），並明確指認各步驟的權責歸屬主體。
- 將工具描述拆解為三大必備要素：穩定名稱、JSON Schema 規範的輸入結構、以及確定性的執行函式。
- 嚴格區分純粹唯讀工具與具備副作用的實體操作工具，並論證為何此劃分是建構 Agent 安全防線的絕對底線。

## The Problem｜問題

LLM 輸出的本質，僅僅是針對下一個 token 的機率分布預測。這就是它的全部輸出介面。若你向純對話模型詢問「班加羅爾現在天氣如何」，它能夠拼湊出一句看似煞有介事的流暢句子，但它絕無可能主動連線至氣象 API。它輸出的語句可能純屬巧合猜中，也可能是三週前的過期幻覺。

彌合這一鴻溝的唯一解法，正是工具介面。宿主程式（Host）——無論是你的 Agent 執行期環境、Claude Desktop、ChatGPT、Cursor 或是自己撰寫的 Python 指令碼——主動向大模型公佈一份允許呼叫的工具清單。當模型研判需要發起操作時，便輸出一個格式嚴格的結構化負載（Payload），明確指名所欲調用的工具名稱及其具體引數。宿主解析該負載，在真實世界中切實執行該工具，並將執行結果反饋給模型。該循環持續迭代，直至模型判斷已獲得充分資訊、不再需要發起任何呼叫為止。

這份協定契約的初代原型於 2023 年 6 月隨 OpenAI 的「functions」參數正式亮相。Anthropic 隨後在 Claude 2.1 中推出了 `tool_use` 區塊；Gemini 亦在數月後跟進引入了 `functionDeclarations`。當今各大主流提供商全面收斂至同一標準形態：輸入帶有 JSON Schema 型別定義的工具清單，輸出標準 JSON 格式的工具呼叫負載。Model Context Protocol（MCP，2024 年 11 月）進一步泛化了這份契約，使單一工具註冊表能無縫服務於任何大模型。A2A 協定（2026 年 4 月，v1.0）則將該原語進一步延伸至 Agent 之間的委派協作。

四步驟迴圈是貫穿所有這些技術的底層不變量。Phase 13 的其餘所有課程，皆是圍繞此核心迴圈的深入展開。

## The Concept｜核心概念

### 步驟一：宣告描述（Describe）

宿主環境透過三大必備欄位對每個工具進行宣告：

- **名稱（Name）**：具備高度穩定性、機器可讀的唯一識別碼。例如 `get_weather`，而非模糊的「weather thing」。
- **說明（Description）**：一段詳盡的自然語言操作指南。例如：「當使用者詢問特定城市的即時當前天氣狀況時使用此工具。嚴禁將其用於歷史天氣資料查詢。」
- **輸入結構（Input Schema）**：描述工具引數型別規範的標準 JSON Schema 物件（Draft 2020-12）。

大模型接收這份工具清單。現代提供商通常利用特定的樣板將這些宣告序列化並編排進系統提示（System Prompt）中，因此身為呼叫端的開發者只需專注於處理結構化定義即可。

### 步驟二：決策發起（Decide）

給定使用者的最新輸入訊息與當前可用的工具清單，模型會自發做出以下三種決策之一：

1. **直接以文字回答**：不發起任何工具呼叫。
2. **呼叫一個或多個工具**：輸出標準的結構化呼叫物件。在 `parallel_tool_calls: true`（OpenAI 與 Gemini 預設啟用，Anthropic 需顯式配置）設定下，模型能在單一輪次中同時輸出多個並行呼叫。
3. **明確拒絕（Refuse）**：在嚴格模式的結構化輸出下，模型可輸出具型別定義的 `refusal` 區塊以表明拒絕執行。

一個合法的工具呼叫負載具備三個穩定的核心欄位：呼叫 `id`、工具 `name` 以及 JSON 格式的 `arguments` 引數物件。id 的存在至關重要，它讓宿主能夠在並行呼叫非同步回傳且順序打亂時，精準將執行結果與最初的呼叫發起點進行相互關聯。

### 步驟三：實體執行（Execute）

宿主接收工具呼叫，依據預先宣告的 JSON Schema 嚴格校驗傳入的引數，隨後呼叫底層執行器（Executor）。引數不合法意味著模型憑空捏造了未定義欄位或傳入了錯誤型別——這在小尺寸或推理能力較弱的模型上極為常見。正式環境的宿主對無效引數通常採行三種應對策略之一：快速失敗並將錯誤訊息直接反饋給模型、利用語法受限解析器自動修復 JSON，或將校驗錯誤注入 prompt 並觸發模型重試。

執行器本體是再普通不過的標準軟體程式碼——Python、TypeScript、Shell 指令或是資料庫查詢。它執行並產出結果，通常為純文字字串，但亦可為任意合法 JSON 結構或富內容區塊（在 MCP 協定中可為文字、圖片或外部資源參照）。該結果必須具備百分之百的可序列化性。

### 步驟四：觀察回饋（Observe）

宿主將工具執行結果封裝並追加至對話歷史中（作為角色為 `tool` 且帶有對應 `id` 的專屬訊息），隨後重新調用模型。此時模型已在上下文（Context）中完整擁有了工具的執行結果，它能夠據此輸出最終的人類可讀解答，亦可發起下一輪新的工具呼叫。此迴圈反覆持續，直至模型自主停止發起呼叫，或宿主觸發了預設的迴圈迭代安全上限。

### 信任劃分：純粹工具 vs 實體副作用工具

依據對真實世界的影響程度，工具嚴格劃分為兩大陣營：

- **純粹工具（Pure Tools）**：唯讀、確定性、無任何外部副作用。例如 `get_weather`、`search_docs`、`get_current_time`。即使投機性頻繁呼叫亦絕對安全。
- **實體副作用工具（Consequential Tools）**：會實質變更外部狀態、產生金錢花費、或存取敏感情資。例如 `send_email`、`delete_file`、`execute_trade`。必須在外層施加嚴密的安全閘門。

Meta 於 2026 年提出的 Agent 安全防護「二元法則（Rule of Two）」明文指出：在單一輪次中，以下三項要素至多僅能同時出現兩項——非可信外部輸入、敏感私有資料、具實體副作用的動作。工具介面正是嚴格落實該安全法則的核心卡點——藉由攔截拒絕呼叫、強制要求人類確認授權、或動態提升權限範圍。詳見 Phase 13 · 15 的完整安全專章，以及 Phase 14 · 09 關於 Agent 層級的權限控制策略。

### 核心迴圈落地的不同場景

| 應用情境 | 誰負責描述（Describe） | 誰負責決策（Decide） | 誰負責執行（Execute） |
|---------|---------------|-------------|--------------|
| 單輪函式呼叫（OpenAI / Anthropic / Gemini） | 應用程式開發者 | LLM 大模型 | 應用程式開發者 |
| Model Context Protocol（MCP） | MCP 伺服器 | 透過 MCP 用戶端調用 LLM | MCP 伺服器 |
| Agent-to-Agent（A2A）協定 | Agent Card 發布方 | 主控發起端 Agent | 被呼叫的受託 Agent |
| 瀏覽器自動化 Agent | 瀏覽器擴充功能 / WebMCP | LLM 大模型 | 瀏覽器自動化執行期環境 |

無論技術名稱如何更迭，底層皆是同一個四步驟迴圈。表格中的列名稱隨情境改變，底層的因果結構始終如一。

### 為何不能僅僅 Prompt 模型輸出 JSON？

「僅在 prompt 中禮貌懇求模型以 JSON 格式回覆」是函式呼叫出現之前的原始過渡手段。在前沿旗艦模型上，這種做法的失敗率約在 5% 到 15% 之間；而在小尺寸模型上失敗率更會急遽飆升。典型的災難場景包含漏括號、末尾逗號、憑空捏造不存在的欄位、以及嚴重的型別錯位。你不得不額外編寫繁複的 JSON 修復腳本、配置昂貴的重試機制，或掛載複雜的約束解碼器。

原生函式呼叫在三個維度上具備決定性優勢：其一，模型提供商在預訓練中便已針對精準呼叫結構展開端到端調校，在嚴格模式（Strict Mode）下有效 JSON 率高達 98% 至 99% 以上；其二，工具呼叫負載被隔離在專屬的協定欄位中，絕不會外溢洩漏至使用者可見的對話文字中；其三，提供商透過語法受限解碼（如 OpenAI strict 模式、Anthropic `tool_use`、Gemini `responseSchema`）在底層實施強制約束，從數學上保證輸出絕對合法。

Phase 13 · 02 將橫向對比三大提供商的 API 實作細節；Phase 13 · 04 將深度剖析結構化輸出的底層原理。

### 斷路器（Circuit Breaker）安全機制

當模型自發停止輸出工具呼叫，或宿主觸發了最大輪次上限時，迴圈才會安全終止。在商業正式環境中，宿主通常將輪次上限嚴格設定在 5 到 20 輪之間。一旦超出此門檻，極可能意味著模型已陷入無法自主收斂的死循環中。Claude Code 預設上限為 20 輪；OpenAI Assistants 為 10 輪；Cursor 的 Agent 模式則為 25 輪。

不加約束的無限迴圈，每隔幾個月就會以「某開源 Agent 一夜之間燒光 400 美元 API 額度」的慘痛災情出現在事後復盤報告中。任何正式上線的系統，絕不可在缺乏斷路器的裸奔狀態下發布。

Phase 14 · 12 將深入探討自我修復與錯誤容錯策略；Phase 17 則將剖析正式環境的速率限制機制。

## Use It｜實際應用

`code/main.py` 在完全不依賴真實外部 LLM 的前提下，完整跑通了標準的四步驟工具呼叫迴圈。程式碼利用一個虛擬的「決策函式」透過樣式比對來模擬模型的智慧決策，而執行器、Schema 校驗器與觀察回饋管理機制皆為百分之百真實的實作。運行該程式碼，親眼觀察完整的請求／回應協同流程與清晰的中間狀態日誌，後續課程中只需將此虛擬決策器替換為真正的模型 API 即可。

核心閱讀重點：

- 工具註冊表（Tool Registry）為每個工具維護四大關鍵欄位：名稱、描述文字、JSON Schema 與實體執行器函式參照。
- 校驗器以純 Python 標準函式庫實作了最小化的 JSON Schema 子集（支援型別、必要欄位、列舉值、數值上下限）。Phase 13 · 04 將提供更完整的工業級解析器。
- 迴圈嚴格將最大迭代次數限制為 5 輪。正式環境中的 Agent 正是依賴此類斷路器來杜絕失控死循環。

## Ship It｜交付成果

本課產出 `outputs/skill-tool-interface-reviewer.md`。給定一份擬定的工具定義草案（名稱 + 說明 + Schema + 執行器大綱），該審查技能將全面評估其是否符合高品質迴圈規範：名稱是否具備機器穩定性、說明文字是否為完備的操作指南、Schema 是否嚴格遵循 JSON Schema 2020-12 規範，以及純粹工具與副作用工具的分類宣告是否清晰無誤。

## Exercises｜練習

1. 在 `code/main.py` 中擴充第四個名為 `get_stock_price(ticker)` 的新工具。為其撰寫清晰的說明文字：「當使用者詢問特定股票代號的當前即時股價時使用此工具。嚴禁將其用於歷史價格走勢或大盤綜合摘要。」運行測試環境，驗證虛擬決策器是否能正確將包含股票代號的提問路由至新工具。

2. 刻意破壞 Schema 校驗流程。傳入一個在 `arguments` 中故意遺漏必要欄位的無效工具呼叫，確認宿主能在真正通電執行前主動攔截並拋出錯誤。隨後傳入一個帶有額外未定義欄位的呼叫。思考並決策：宿主應該主動拒絕執行，還是寬容忽略該多餘欄位？請以系統安全性為出發點論證你的技術選擇。

3. 將測試環境中的所有工具嚴格標註為「純粹（Pure）」或「具備副作用（Consequential）」。為需要防護的註冊表條目加上 `consequential: true` 旗標，並修改核心迴圈，使其在挑選到副作用工具時主動暫停並印出「需先向使用者取得授權確認」的提示。這正是所有商業級宿主不可或缺的授權閘門原型。

4. 在紙上親手繪製四步驟迴圈架構圖，並針對你最常用的用戶端工具（Claude Desktop、Cursor、ChatGPT 或自研堆疊），填寫各步驟的具體權責歸屬。並對照 Phase 13 · 06 中專屬於 MCP 協定的具體演化變體。

5. 從頭到尾精讀 OpenAI 官方函式呼叫指南。找出請求酬載中存在、但本課四步驟最簡迴圈中並未顯式列出的一個額外進階欄位。深入分析該欄位帶來了何種增強功能，以及為何它屬於便利性擴充而非不可或缺的核心骨架。

## Key Terms｜關鍵術語

| 術語 | 常見俗稱 | 實際意義 |
|------|----------------|------------------------|
| Tool | 「大模型可呼叫的工具」 | 由「名稱 + JSON Schema 定義的輸入規格 + 實體執行器函式」組成的三元組契約 |
| Function calling | 「原生函式呼叫」 | 提供商在 API 底層直接支援輸出結構化呼叫負載、而非混雜自由文字的原生機制 |
| Tool call | 「模型的行動請求」 | 模型輸出的標準 JSON 結構，包含唯一的 `id`、目標工具 `name` 以及傳入的 `arguments` |
| Tool result | 「工具執行成果」 | 執行器函式的真實運算產物，包裝於角色為 `tool` 且帶有相應 id 的專屬訊息中回傳 |
| Parallel tool calls | 「多工具並行呼叫」 | 模型在單一思考輪次中同時輸出多個互相獨立、可藉由 id 異步關聯的工具呼叫物件 |
| Strict mode | 「保證百分之百合法」 | 底層採用語法受限解碼技術，在數學上保證模型輸出絕對符合宣告的 JSON Schema |
| Pure tool | 「純唯讀查詢工具」 | 不會變更任何外部狀態、無副作用的工具；允許被系統反覆且安全地投機性預先執行 |
| Consequential tool | 「具實體副作用的動作」 | 會實質修改外部狀態、產生金錢開銷或涉及個資的操作；必須掛載授權審核閘門 |
| Four-step loop | 「工具調用核心生命週期」 | 宣告描述（describe）→ 決策發起（decide）→ 實體執行（execute）→ 觀察回饋（observe） |
| Host | 「Agent 宿主執行期」 | 負責維護工具註冊表、向大模型發起呼叫、並在實體環境中執行工具程式碼的主控程式 |
