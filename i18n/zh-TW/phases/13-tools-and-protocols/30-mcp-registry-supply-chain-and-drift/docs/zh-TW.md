# MCP 註冊表供應鏈：准入審查、運行漂移與安全回滾

> 註冊表條目僅代表發布者當初的單方面宣告。生產級准入審查則確鑿證明：你究竟下載了什麼、實體觀測到了什麼、內部核准了什麼，以及遭遇事故時能安全復原至何種狀態。

**Type:** Build
**Languages:** Python
**Prerequisites:** Phase 13 · 17 (gateways and registries), Phase 13 · 18 (production authentication)
**Time:** ~90 minutes

## Learning Objectives｜學習目標

- 嚴格區分註冊表發布（Publication）、套件來源出處（Provenance）、執行時期發現（Discovery）與本地審核核准（Approval）四大獨立防護層。
- 嚴格校驗 MCP 伺服器命名空間，絕不盲目信任註冊表紀錄內部所宣稱的名稱文字。
- 完整鎖定不可變的發布資料、執行來源、來源憑證與線上即時描述元客觀證據。
- 在准入審查確立後，持續即時偵測註冊表狀態異動與執行時期行為漂移（Runtime Drift）。
- 在不竄改歷史記錄的前提下，將流量路由平滑回滾至先前已獲准入的受信任版本。
- 維護具備防篡改能力的准入審查帳本（Ledger），為每項系統決策提供可審計的客觀證據。

## The Problem｜問題

你在公開註冊表中找到了 `com.example/inventory`。其功能描述看似完全切題；其實體套件確實存在；且該伺服器在線上能正常回應 `server/discover`。

這絕非單一事實，而是一條由多個不同法定授權機構所串聯而成的聲明鏈：

1. 具備該命名空間身分認證的發布者，提出了一份伺服器發布記錄。
2. 特定套件註冊中心（Package Registry）提供了一份具備特定身分與雜湊摘要的實體產物。
3. 正在運行的實體端點對外回報了協定版本、支援能力清單、工具描述元與診斷伺服器資訊。
4. 你的企業組織經過評估，正式判定該精確組合獲准在內部生產系統中上線。

若將這些事實簡化為「既然在註冊表中，就可以信任它」，會造成嚴重的軟體供應鏈盲區。一份原本合法的發布記錄隨後可能被宣告廢止；若未鎖定套件實體雜湊，套件標籤可能被惡意指向非預期的危險產物；伺服器在通過審查後，可能在線上動態注入破壞性工具；而回滾機制可能會在不知不覺中切換至一個從未通過審查的未知版本。

唯一解法是在每道系統邊界皆建立具備客觀證據支撐的准入控制器（Admission Controller）。

## The Registry Is an Index, Not Your Approval System｜註冊表是索引目錄，而非你的審批授權系統

官方 MCP Registry 負責儲存伺服器後設資料。其 `server.json` 記錄標註了伺服器版本號，並宣告了一個或多個套件或遠端端點。發布規則進一步實施了命名空間身分驗證、套件所有權檢查、受限註冊中心規則，以及限定的發布者後設資料路徑。

這些控制措施回答的是**發布合規性問題**。然而，你的正式環境安全策略依然必須回答關鍵的**部署授權問題**：

| 防護邊界 | 核心檢核問題 | 證據權威來源 |
|---|---|---|
| 命名空間 | 發布者是否確實獲准使用該名稱？ | 註冊表身分認證搭配經過驗證的本機命名空間輸入 |
| 發布記錄 | 發布者針對該版本具體宣告了什麼？ | 不可變的 `server.json` 密碼學雜湊摘要 |
| 執行來源 | 究竟哪份套件或遠端端點將實質執行？ | 宣告的來源欄位、驗證的所有權結果、傳輸模式與受信雜湊 |
| 執行時期 | 該實體端點當前在線上暴露了哪些能力？ | `server/discover` 回傳內容與工具描述元清單 |
| 准入審查 | 內部策略是否已正式批准該精確集合？ | 本機鎖定記錄與審查帳本條目 |
| 維運治理 | 該版本是否依然安全，且可用何者替換？ | 漂移偵測、狀態同步、健康檢查與回滾路由策略 |

註冊表 Schema 版本與 MCP 協定版本各自完全獨立。一份記錄可能採用已發布的 `2025-12-11` 伺服器記錄 Schema，而其線上實體伺服器則支援 MCP `2026-07-28` 協定。切勿依據其中一者主觀臆測另一者。

```figure
mcp-registry-admission
```

## Seven Controls in One Admission Decision｜單次准入決策中的七大核心防線

### 1. 命名空間嚴格核驗

官方 Registry 名稱採用經過身分驗證的命名空間。經校驗的網域名稱會對映為反向網域名稱前綴。例如，取得 `example.com` 的控制權，方能確立 `com.example/*` 命名空間。

切勿採用單純的字串前綴檢查：

```python
server_name.startswith("com.example")
```

這會將惡意的 `com.exampleevil/tool` 判定為合法放行！應當嚴格依 `/` 切割名稱、要求非空的 Slug 片段，並對命名空間進行完全一致的比對。更關鍵的是：必須自認證結果中將經過驗證的命名空間傳入准入控制器，絕不可直接自未經審查的記錄文字中提取信任。

基於 GitHub 與基於網域名稱的命名空間採用不同的認證途徑。應當將任一途徑正規化為單一准入輸入：經過嚴格驗證的命名空間字串。

### 2. 來源出處交叉驗證（Provenance Join）

針對套件型記錄，宣告內容與實體下載的產物必須在以下關鍵欄位上實施完全一致的交叉校驗：

- 套件註冊中心型別；
- 套件唯一識別碼；
- 套件版本號；
- 經過驗證的套件所有權結果；
- 下載產物的實體密碼學雜湊摘要。

同時必須嚴格校驗宣告的套件傳輸層模式。僅宣告遠端端點的記錄同樣合法，絕不可因其缺少實體套件而予以拒絕。針對遠端來源，將宣告的 URL 與傳輸型別，與經過獨立驗證的端點所有權以及受信連線／部署憑證雜湊完整交叉綁定。

本課程式碼同時支援這兩種來源型別，並將選定的來源連同註冊表來源、伺服器名稱、註冊表版本、記錄雜湊與憑證雜湊一同進行全域雜湊計算。產出的出處雜湊（Provenance Digest）是指向完整證據集合的精準指標，但它絕無法取代保留原始證據本身的必要性。

切勿單純採信由待驗證產物自身所提供的雜湊數值。必須在受信任的下載邊界處實質計算該雜湊，或由經過驗證的受信套件服務直接提供。

### 3. 鎖定全域決策，而非單純鎖定版本號

註冊表版本號是不可變的唯一發布標識。發布的後設資料具有不可變性；任何變更皆必須升級為全新版本號。官方強烈建議遵循語意化版本（Semantic Versioning），但 Registry 本身並不強制要求，且**堅決不接受**任何版本範圍宣告。

這意味著 `^1.4` 或「latest」根本不具備准入鎖定效力。一個合格的生產鎖定條目必須包含：

```json
{
  "server": "com.example/inventory",
  "version": "1.0.0",
  "recordDigest": "...",
  "source": {"kind": "package", "registryType": "pypi"},
  "sourceDigest": "...",
  "toolsetDigest": "...",
  "provenanceDigest": "...",
  "registryStatus": "active"
}
```

多層次鎖定能讓你在故障時精準定位破壞發生的具體邊界：在相同版本下記錄雜湊發生變更，代表註冊表本體完整性受損；在相同座標下來源雜湊發生變更，代表底層執行來源遭遇竄改；而工具集雜湊發生變更，則代表線上端點發生了執行時期漂移。

### 4. 線上即時漂移偵測

准入審查必須直接對實質接收業務流量的線上伺服器進行實地觀測。調用 `server/discover`、透過受信通道檢索暴露的工具描述元清單，並強制核驗：

- `2026-07-28` 確實包含於 `supportedVersions` 清單中；
- 本機要求的所有關鍵能力全數存在；
- 每個工具描述元皆具備必備的身分識別與 Schema 定義；
- 正規化後的描述元雜湊與先前准入鎖定的雜湊完全吻合。

回傳結果中選填的 `_meta["io.modelcontextprotocol/serverInfo"]` 數值僅代表自我宣稱的展示、日誌與除錯脈絡資訊。應將其記錄為診斷證據，但**絕不可**依此建立命名空間、套件所有權、端點所有權、准入許可或任何其他安全決策。`_meta` 外部的直接 `serverInfo` 別名並非標準協定欄位，絕不可被採納為診斷依據。

僅對排序無實質語義影響的欄位實施正規化。範例程式碼在計算雜湊前按穩定名稱對工具清單進行排序，確保單純的清單排序變化不致誤報為漂移；但它絕不捨棄描述元內的任何具體欄位。新增工具、修改 Schema、調整描述文字或新增標註，皆會改變鎖定雜湊。

範例實作將畸形描述元與任何描述元雜湊異動全數視為重大漂移：立刻隔離該鎖定條目、自活動路由表中撤下，並禁止將該版本選作回滾目標。在正式環境策略中，即便僅是純文字描述的微小修飾也必須重新走過審查流程，因為描述文字會直接左右大模型的工具選取行為。「微不足道」的文字變更同樣會實質改變 agent 的決策邏輯。

### 5. 註冊表狀態屬於即時變動狀態

Registry API 會在每筆伺服器記錄旁附帶一個回應層級的 `_meta` 物件。由註冊表官方所管理的系統欄位存放於 `_meta["io.modelcontextprotocol.registry/official"]` 底下。將回應層級的 `_meta` 物件傳入准入控制器，並讀取 `_meta["io.modelcontextprotocol.registry/official"].status`。直屬的 `_meta.status` 數值並非官方標準線路格式。切勿將回應層級後設資料與發布記錄本身的內部 `_meta` 互相混淆。其狀態包含：

- `active`：預設對外暴露，合乎本機准入資格；
- `deprecated`：依然可被發現但附帶警告，不再適合自動化調用；
- `deleted`：自預設清單中隱藏，但歷史記錄依然能透過已刪除或增量檢視端點存取。

准入確立後必須定期同步該狀態。一旦原本活躍的版本被宣告廢止或刪除，必須立刻隔離其鎖定條目並停止向其分流新任務。同時必須完整保留歷史審查證據；自預設清單中移除，絕非將內部審計日誌銷毀抹除的藉口。

發布者自訂的後設資料嚴格僅能存放於發布記錄內部的 `_meta.io.modelcontextprotocol.registry/publisher-provided` 之中。由註冊表管理的系統狀態是完全獨立的。絕不可讓發布者自行定義其官方狀態。

### 6. 回滾本質上是路由狀態的復原

不可變的發布記錄在回滾過程中絕不會被修改。回滾是自歷史上已獲准入且當前依然合規的鎖定條目中，挑選合適者並將活動路由指向它。

一個安全的回滾目標必須同時滿足：

1. 具備完整的已完成准入記錄；
2. 在當前系統策略下依然維持 active 註冊表狀態；
3. 未被任何執行時期或資安證據所隔離；
4. 依然能精準解析為當初鎖定的套件產物與線上描述元集合；
5. 通過即時的健康檢查。

範例程式碼聚焦於前三項核心條件。在真實生產系統中，調解器在正式切換流量前，應當重新抓取該套件並對線上端點實施二次確認。

### 7. 追加式准入審查帳本（Admission Ledger）

准入資料庫僅說明當前何者處於活躍狀態；而審查帳本則詳述其背後「為何如此」的完整依據。

每個範例帳本條目皆包含：遞增序號、時間戳記、事件型別、伺服器名稱、版本號、決策結果、裁決原因、客觀證據、前一條目的雜湊值以及自身雜湊值。篡改任何過往記錄，會瞬間導致該條目及其後續所有雜湊鏈結全數斷裂。

這屬於防篡改可識別機制（Tamper-evident），而非天然具備防篡改免疫力（Tamper-proof）。應當定期將帳本頂層雜湊錨定至獨立的信任網域中（例如具備數位簽名的發布後設資料或單寫多讀 WORM 儲存裝置）。嚴格限制帳本追加權限；授權權杖、套件密鑰、工具輸入參數與內部端點機密嚴禁洩漏至證據日誌中。

## Build It｜動手實作

可直接運行的控制器位於 `code/main.py`，全套實作立足於純 Python 標準函式庫。

運行確定性演示程式：

```bash
cd phases/13-tools-and-protocols/30-mcp-registry-supply-chain-and-drift
python3 code/main.py
```

演示程式依序執行五項核心操作：

1. 准入 `1.0.0`：完整核驗命名空間、套件來源出處、協定版本、能力宣告與工具清單；
2. 准入 `1.1.0` 並將其標記為活躍路由；
3. 在執行時期即時偵測到一個未經審查的非預期 delete 刪除工具；
4. 偵測到 `1.1.0` 在註冊表中的官方狀態變更為 `deprecated`；
5. 將活動路由安全回滾至依然維持合法准入狀態的 `1.0.0`。

預期輸出結構：

```json
{
  "admitted": [true, true],
  "driftAllowed": false,
  "rollbackAllowed": true,
  "activeVersion": "1.0.0",
  "ledgerValid": true
}
```

請依以下順序研讀實作程式碼：

1. `namespace_for_domain()` 與 `namespace_matches()` 確立精確的命名授權邊界；
2. `digest()` 與 `normalized_tools()` 產出確定性的密碼學證據；
3. `RegistryAdmissionController.admit()` 綜合完成發布記錄、來源出處、線上端點與系統策略的四方會審；
4. `check_live()` 將最新線上觀測與鎖定基準進行比對；
5. `observe_registry_status()` 自動隔離註冊表狀態發生變更的版本；
6. `rollback()` 僅允許切換至歷史上已獲准入且合乎資格的目標；
7. `AdmissionLedger.verify()` 即時檢測歷史記錄是否曾遭惡意篡改。

## Use It｜實際應用

將准入控制器安插於服務發現與流量路由之間：

```text
Registry sync -> artifact verifier -> live discovery -> admission controller -> route table
                                               |                 |
                                               v                 v
                                          evidence store    admission ledger
```

為這些獨立工作指派不同的權限身分。註冊表同步工作僅需後設資料讀取權限；產物驗證器需要套件下載存取權限；路由調解器僅需啟用已獲核准條目的權限。任何單一角色皆不應坐擁所有金鑰。

明確劃分發布狀態：「Approved」代表客觀證據符合策略；「Active」代表流量路由當前正選中它；「Quarantined」代表其已被隔離不得接收新任務；「Superseded」代表已被其他新版所取代。切勿將這四種獨立語義粗暴揉合成單一布林值。

在工具清單正式暴露給用戶端（`tools/list`）之前，必須強制完成准入審查。否則用戶端極易在發布與策略審核的時間差窗口中，誤調用尚未獲准的危險工具。

## Interactive Lab｜互動實驗

你將親手觀察系統如何在各邊界上精準攔截違規。

### 實驗 A：命名空間衝突攔截

在程式碼目錄下開啟 Python 互動式環境：

```bash
cd phases/13-tools-and-protocols/30-mcp-registry-supply-chain-and-drift/code
python3 -q
```

隨後執行：

```python
from main import namespace_matches
namespace_matches("com.example/inventory", "com.example")
namespace_matches("com.exampleevil/inventory", "com.example")
```

第一個輸出為 `True`；第二個輸出為 `False`。嘗試在本地將精確比對修改為 `startswith`，親眼觀察惡意名稱如何趁虛而入。在繼續前務必恢復原本的精確比對。

### 實驗 B：描述元漂移偵測

```python
from main import *
times = iter(f"2026-08-21T12:00:{n:02d}+00:00" for n in range(10))
c = RegistryAdmissionController(clock=lambda: next(times))
meta = {OFFICIAL_META_KEY: {"status": "active"}}
c.admit(sample_record("1.0.0"), meta, "com.example", evidence_for("1.0.0"), sample_live("1.0.0"))
c.check_live("com.example/inventory", "1.0.0", sample_live("1.0.0", True))
```

檢視拒絕理由與路由狀態。實體套件與註冊表記錄皆未發生任何變更；然而由於線上工具能力發生了漂移，控制器立刻果斷隔離並撤下了該鎖定條目。這正是軟體供應鏈治理必須在安裝後持續即時監控的根本原因。

### 實驗 C：狀態廢止與安全回滾

准入 `1.1.0`，將其標記為 deprecated，並分別嘗試兩個回滾目標：

```python
c.admit(sample_record("1.1.0"), meta, "com.example", evidence_for("1.1.0"), sample_live("1.1.0"))
c.observe_registry_status("com.example/inventory", "1.1.0", "deprecated")
c.rollback("com.example/inventory", "1.1.0", "unsafe retry")
c.rollback("com.example/inventory", "1.0.0", "restore known release")
c.ledger.verify()
```

被隔離的目標被果斷拒絕；而先前健康的活躍鎖定版本則順利復原；全域帳本驗證依然完全合法。

## Practice Lab｜實戰實驗

為控制器擴充「雙人審批（Two-person approval）」安全關卡。

具體需求：

- 將審批記錄儲存為具備數位簽名的客觀證據參照，而非鎖定條目中的可變字串；
- 當工具集中包含標註 `destructiveHint: true` 的破壞性工具時，強制要求兩名不同的審核人員身分核准；
- 果斷拒絕重複的審核者身分；
- 當審批未完備時，在帳本中忠實記錄初次的准入失敗嘗試；
- 撰寫單元測試覆蓋：0 人審批、1 人審批、重複身分審批與 2 名獨立審核員審批通過等全部情境；
- 審計日誌中嚴禁洩漏數位簽章明文、金鑰憑證或完整的私有工具參數。

成功標準：包含破壞性工具的伺服器，唯有在兩名獨立人員皆對精確的記錄雜湊、套件雜湊與工具集雜湊簽名核准後，方獲准進入活躍狀態。

## Production Failure Modes｜正式環境失效模式

| 失效情境 | 發生根本原因 | 正確架構處置準則 |
|---|---|---|
| 名稱看似合法但命名空間未曾認證 | 策略盲目信任記錄內的自述文字 | 拒絕准入，直到受信驗證器提供精確的前綴授權依據 |
| 相同套件座標回傳了全新位元組 | 上游套件庫遭篡改或供應鏈污染 | 立即停止啟用，保留新舊雙方雜湊，深入排查下載通道 |
| 「latest」未經審查擅自更新 | 浮動標籤選取機制逃逸了精確鎖定 | 嚴格僅解析與綁定精確的已准入版本號與實體雜湊值 |
| 審核通過後線上突發全新工具 | 執行時期發生漂移或指向不同部署 | 立刻隔離該路由，重新捕獲並審查全新的描述元清單 |
| 已宣告廢止的版本依然在接收流量 | 狀態同步機制缺漏或發生延遲 | 設定定期定時狀態同步，並在正式啟用前強制核驗狀態 |
| 已刪除記錄在預設同步中消失 | 用戶端僅請求了活躍記錄清單 | 採用增量或感知刪除狀態的同步端點，完整保留本機歷史 |
| 回滾目標版本從未通過准入審查 | 路由控制系統與審批狀態完全脫節 | 堅決拒絕回滾，要求該目標版本必須重新走過完整准入流程 |
| 攻擊者重寫整條帳本後通過本機驗證 | 雜湊鏈缺乏外部受信任錨點 | 將帳本頂層雜湊定期發布至獨立的外部信任網域 |
| 證據日誌中殘留 Bearer 權杖或參數 | 日誌模組粗暴複製了整個完整請求 | 在收集當下實施強制抹除，僅記錄最小必要的證明資訊 |

## Operational Rule｜維運準則

發布規則回答的是「該身分能否在註冊表中認領此名稱？」而准入控制器回答的是「我們是否願意在內部實質執行這份精確產物、並對外暴露其精確行為？」請始終將兩者清晰剝離、鎖定每道交叉邊界，並確保回滾始終依據客觀證據做出決策。
